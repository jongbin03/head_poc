### 1.1 가장 중요한 발견 — 분산 로드는 원래 망가져 있었다

`device_map="auto"`로 모델을 쪼개면 accelerate가 출력을 메인 device로 모으는데,
그때 `out.attentions[l]`은 **원본이 아니라 복사본**이다. 복사본은
`target_logit → inputs_embeds` 경로 밖의 막다른 가지라 backward가 지나가지 않고,
거기 건 훅도 안 불린다.

**실측(7B, 3 GPU): 28개 레이어 중 layer 0(=유일하게 device 이동이 없던 레이어)만
점수가 남고 나머지 27개가 전부 0.** 상위 head 20개가 전부 layer 0이 됐다 —
`plan-2026-08-26.md` 6절이 정의해둔 S4→S5 게이트 실패 조건에 정확히 걸렸다.

**이건 태스크 A가 만든 버그가 아니다.** 구버전 `retain_grad()`도 복사본에는 `.grad`가
안 채워져 `if a.grad is None: continue`로 **조용히** 스킵했다. 즉 예전 문서의
*"device_map auto가 안 된다는 건 OOM 로깅이 device 0만 보는 표시 문제였지 정확성
문제가 아니다"* 라는 판단은 **틀렸다**. 정확성 문제가 맞았고, 아무도 눈치채지 못하게
조용했을 뿐이다.

**수정**: `self_attn` 모듈에 forward 훅을 걸어 **모듈이 방금 만든 원본 텐서**에
backward 훅을 건다. 그리고 전 레이어가 계산되지 않으면 **`RuntimeError`로 죽인다** —
0으로 남은 레이어가 있으면 topk가 그걸 하위로 밀어내 "에러 없이 그럴듯하지만 틀린"
head 집합이 나오는데, 이 코드베이스가 가장 경계해온 실패 모드다.

### 1.2 발표에 쓸 수 있는 오늘의 수치

**지시 1(suite 균등화)** — 원인이 **세 겹**이었다:
1. 어댑터가 첫 tool 턴만 봄 → 일반화로 해결 (travel 8→59)
2. OOM이 긴 suite를 골라 죽임 → **태스크 A로 대부분 해결** (전체 55.5%→85.2%,
   travel 18%→80%, workspace 19%→60%)
3. 그래도 최장 길이(T>~1500)는 단일 24GB에서 구조적으로 불가능 → **잔존**

**지시 2(스케일업)** — 32B는 단일 24GB로 불가능(4bit 가중치 18GB + attention).
3장 분산으로 **가능함을 확인**(가중치 19.2GB, 카드당 최대 8.6GB).

**knockout 평가** — baseline 공격 성공 1건(1/59)이 knockout으로 완전 억제(1/1).
7/31·8/19 세 번의 이전 실행(2%대 baseline, 3/3 억제)과 **같은 패턴이 재현**됐다.

## 3. 새 서버 (Pro 4500 + A6000) 활용안

오늘 새로 구성됐다는 서버. 기존 Titan RTX ×3(24GB, Turing)과 비교해 두 가지가 바뀐다:

1. **둘 다 bf16 네이티브** — Titan은 에뮬레이션으로 +13% 오버헤드를 감수 중이었다.
   dtype은 여전히 bf16이라 **기존 결과와 같은 표에 놓을 수 있다**(계획서 1.3절 조건 유지).
2. **A6000 48GB 한 장** — 32B를 쪼개지 않고 올릴 수 있을 가능성. 분산은 순차 실행이라
   느리므로 단일 카드가 훨씬 빠르다.

**추천 배치 — 두 축을 동시에** (S6 미도달 위험이 사라진다):

| 카드 | 실험 |
|---|---|
| A6000 48GB | Qwen2.5-32B (스케일 축, S4→S5) |
| Pro 4500 32GB | Llama-3.1-8B (패밀리 축, S6). 코드 수정 0 |
| Titan ×3 (기존) | 7B 재실행·eval 등 |

**⚠️ 셋업 함정 — Pro 4500은 Blackwell(sm_120)이라 cu126으로는 안 돈다.**
현 서버는 `torch 2.13.0+cu126`인데 새 서버는 **cu128 이상** 필요
(`requirements.txt`에 이미 적어둔 이슈). A6000(sm_86)은 둘 다 되니 **cu128 하나로
두 카드 커버**. 설치 후 검증:

```bash
python -c "import torch; print(torch.__version__, torch.cuda.get_arch_list())"
# sm_120 과 sm_86 이 둘 다 있어야 함
```

그리고 **torchvision은 반드시 torch와 같은 index-url에서** 받을 것 — 안 그러면
`operator torchvision::nms does not exist`로 transformers import 자체가 죽는다
(8/21 실측).

**새 서버 첫 검증**: `run_pipeline.py --model Qwen/Qwen2.5-0.5B-Instruct --dataset_limit 3`
으로 `jaccard(read,internal) = 0.212`가 나오는지. 이게 통과해야 결과를 기존 표에 섞을 수 있다.

## 4. 32B 메모리 — 단일 카드로 가능한가

측정된 것: **4bit 가중치 19.2GB** (3장 합계, 카드당 최대 8.6GB).

하지만 **가중치만으로 판단하면 안 된다.** 7B 실측에서 가중치는 5.7GB인데 T=1500
relevance 계산의 피크는 **22.23GB**였다 — 가중치 외에 16.5GB(attention 텐서,
Q/K/V·MLP 중간값, autograd가 붙든 activation)가 더 들었다.

32B는 64층×hidden 5120이라 그 부분이 7B(28층×3584)의 3배 이상이다. 거친 추정:

| | 가중치 | attention | 기타 activation | 합계(추정) |
|---|---|---|---|---|
| 32B, T=1000 | 19GB | ~5GB | ~28GB | **50GB+** |
| 32B, T=1500 | 19GB | ~11GB | ~42GB | **70GB+** |

**추정이므로 직접 재는 게 정확하다.** 32B가 올라가 있을 때:

```bash
python -u -c "
import torch
from attn_relevance import load_model_for_relevance, compute_head_relevance
model, tok, dt = load_model_for_relevance(
    'Qwen/Qwen2.5-32B-Instruct', four_bit=True,
    device='cuda:0', device_map='auto', model_family='qwen2')
T = 1200
ids = torch.randint(0, tok.vocab_size, (1, T), device='cuda:0')
spans = {'data_inj': list(range(T//2, T//2+50))}
for d in range(torch.cuda.device_count()): torch.cuda.reset_peak_memory_stats(d)
compute_head_relevance(model, ids, 100, spans)
torch.cuda.synchronize()
print('per-GPU peak GB:', [round(torch.cuda.max_memory_reserved(d)/2**30,2)
                            for d in range(torch.cuda.device_count())])
print('합계:', round(sum(torch.cuda.max_memory_reserved(d)
                        for d in range(torch.cuda.device_count()))/2**30, 2))
"
```

이 "합계"가 **A6000 48GB에 32B를 단독으로 올릴 수 있는지**의 답이다.

## 6. 발표 관점 — 최악의 경우 (중요)

**32B가 끝까지 안 돼도 발표는 성립한다.** 오늘 확보한 것만으로:

- **지시 1**: 원인 세 겹 규명 + 태스크 A로 생존율 55.5%→85.2% 개선을 **수치로** 제시
- **지시 2**: "단일 24GB로는 메모리상 불가능, 3장 분산 필요"를 근거표와 함께 보고.
  분산이 실제로 동작함까지 확인(가중치 19.2GB). **덤으로 "분산 경로에 조용한
  정확성 버그가 있었고 찾아서 고쳤다"는 것 자체가 결과다**
- **지시 4**: user_task group split + `--eval_split heldout` 연결 완료
- **지시 3**: 합성 한정 예비 결과 + 선행 조건(재라벨링) 설명

**무리하지 말 것.** 남은 시간은 32B 완주보다 **발표 자료 정리**에 쓰는 편이 나을 수
있다. 32B는 "돌려봤고 여기까지 나왔다"로 보고해도 지시 2는 충족된다.
