## 3. 결과에 따른 분기

### (A) suite별 생존율이 고르다 (전부 60%+)

→ **바로 S4(32B)로 간다.** 파라미터는 7B와 동일하게 시작하되, 32B는 64층×64헤드로
attention 텐서가 7B의 약 4~5배이므로 **`--batch_size 3`, `--max_seq_len 1500`** 으로
낮춰서 먼저 소규모(`--head_n 40`) 시험 실행 후 본 실행.

### (B) travel/workspace만 생존율이 낮다 ← **예상되는 결과**

8/21 관찰: `s2_expandable` 실행에서 배치 0~50은 5/5 성공인데 배치 105~154는 0~1/5였다.
`head_pairs`가 **suite 블록 순서**(banking 37 → slack 41 → travel 38 → workspace 38)라
후반이 곧 travel/workspace다. 두 suite는 프롬프트가 길다 (중앙값 travel 1420,
workspace 1378 vs banking 740, slack 409).

→ **suite를 균등하게 뽑아도 OOM이 긴 suite를 골라서 죽인다.** 샘플링에서 맞춘 균형이
relevance 계산 단계에서 다시 깨진다. 이 경우 두 갈래:

| 방향 | 내용 | 장단 |
|---|---|---|
| **(B-1) `--max_seq_len` 하향** | 2000 → 1200~1500 | 손실이 **무작위 OOM이 아니라 명시적 필터**가 되어 suite별로 사전에 알 수 있다. 정직하지만 표본이 준다. **발표까지 5일이면 이쪽이 안전** |
| (B-2) relevance 메모리 개선 | `output_attentions=True`가 **모든 레이어의 attention + gradient를 동시에** 들고 있다. 7B·T=2000이면 이것만 수 GB. 레이어별 hook으로 즉시 축약 후 폐기 | 근본 대응이고 32B에 결정적. 다만 `compute_head_relevance` 재작성이라 리스크 있음 |

**권장**: 발표용으로는 (B-1)로 결과를 확보하고, (B-2)는 이월. 단 (B-1)로 갈 때
`max_seq_len`별 suite 잔존 수를 먼저 재고 결정할 것:

## 4. 미해결 — 다음 세션에서 처리할 것

### 4.1 `head_pairs`가 suite 블록 순서다 (우선순위 높음)

`pair_sampling.stratified_group_split`이 stratum별로 순회하며 append하므로 결과가
suite 블록으로 쌓인다. 문제 두 가지:

- 중간에 죽으면 **특정 suite가 통째로 날아간다**
- "후반 배치에서 OOM이 는다"처럼 **원인을 오독하게 만든다** (실제로는 suite 차이)

→ 최종 `head_pairs`를 같은 seed로 한 번 더 섞을 것. eval 쪽도 동일.

### 4.2 OOM 진단 계측 (필요해지면)

(c) 남의 점유를 구분할 수 있다:

- OOM 메시지에 `seq_len`, `torch.cuda.memory_reserved()`, `memory_allocated()`,

## 5. 확정된 사실 — 재검증 불필요

다음 세션에서 다시 파헤치지 말 것. 전부 실측으로 확정됐다.

| 항목 | 결론 | 근거 |
|---|---|---|
| **dtype** | **bf16 고정** | fp16은 7B+AgentDojo에서 **20/20 NaN**. 0.5B 합성에서도 1/3 NaN. loss scaling으로 못 살림(scale 0.01/1/100에서 NaN 개수 동일 = forward overflow). bf16 에뮬레이션 오버헤드는 fp32 대비 +13%뿐 |
| **환경** | Miniforge+conda env(python 3.11), `PYTHONNOUSERSITE=1`, torchvision을 torch와 같은 인덱스에서 | `env.sh`, `run-guide.md` 부록 A |
| **pair 수** | **307쌍** (기존 220 + 일반화로 87 회복) | travel 8→59. `never=0`(주입은 항상 대화에 있음) |
| **길이** | 신규 87쌍 전부 **1945토큰 미만** | 일반화로 프롬프트가 길어질 걱정은 없었음 |
| **`max_seq_len` 상향은 무의미** | 2000→6000으로 올려도 207→209 | 길이 필터는 6%만 자름 |
| **OOM은 길이 의존** | 단편화가 아님 | `expandable_segments`로 81/150 → 85/154 (비율 54%→55%, 사실상 무변화) |
| **`--batch_size`** | 5 이하 유지. 늘리지 말 것 | 16GB/batch5=105/150 vs 24GB/batch15=74/150 |

## 6. 8/26 발표에서 **정정**할 것

이번 조사로 이전 발표 내용 중 틀린 것이 드러났다.

1. **"travel은 OOM으로 제외됐다" → 오진.** travel은 relevance 계산에 들어가기도 전에
   pair 생성 단계에서 140조합 중 8개로 줄어 있었다. 원인은 어댑터가 **첫 tool 턴만**
   보는 것이었고, travel은 주입이 턴 2~4에서 나타난다. 일반화 후 8→59.
2. **suite 불균형은 구조적이다.** workspace가 전조합의 59%(560/949)를 차지한다.
   무작위로 뽑으면 필연적으로 독점한다.
3. **`split_pairs`는 held-out이 아니었다.** pair 단위로만 나눠 같은 user_task가
   탐색셋과 평가셋 양쪽에 들어갔다. 프롬프트의 system/user 질문/history를 전부 공유한다.
   → `user_task` 단위 group split으로 수정, 평가 쪽도 `--eval_split heldout`으로 연결.
