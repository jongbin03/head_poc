### 1.2 메모리 계산 — 32B는 단일 GPU로 불가능

`attn_relevance.compute_head_relevance`가 `output_attentions=True`로 **모든 레이어의
attention을 동시에** 들고, `retain_grad()`가 **gradient까지 또 한 벌** 들고 있다.

attention 텐서 총량 = `층수 × 헤드수 × T² × 2바이트`, gradient까지면 그 **2배**.

| 모델 | 층×헤드 | T=2000 | T=1500 | T=1000 |
|---|---|---|---|---|
| 7B | 28 × 28 | **12.5GB** | 7.1GB | 3.1GB |
| 32B | 64 × 40 | 41GB | 23GB | **10.2GB** |

32B는 4bit 가중치만 **18GB**다. T=1000이어도 `18 + 10.2 = 28GB > 24GB`.
**단일 24GB 카드로는 어떤 길이에서도 안 된다.**

### 1.3 태스크 A 완료 + 실측 검증 (2026-08-24)

`attn_relevance.compute_head_relevance`를 `retain_grad()` → `register_hook`으로
교체했다 (커밋 `ebaa707`). 계산 로직은 동일 — `ReLU(attn × grad)`를 span에 합산하는
것을 backward가 끝난 뒤 한 번에 하던 걸, 각 레이어 gradient가 나오는 즉시 하도록
옮겼을 뿐이다.

**수치 동일성 검증** — 서버 실측, `Qwen2.5-0.5B-Instruct`, `dataset_limit=3`:
`jaccard(read,internal) = 0.212`. 태스크 A 계획 당시 적어둔 기준값과 **정확히 일치**
(`results/2026-08-21_Qwen-Qwen2-5-0-5B-Instruct_bf16/summary.txt`). 계산 결과가
바뀌지 않았음을 확인.

**메모리 검증** — `Qwen2.5-7B-Instruct` 4bit, 합성 랜덤 토큰 입력으로 attention 항만
분리해서 측정 (`compute_head_relevance`를 직접 호출, `torch.cuda.max_memory_reserved()`):

| T | 훅 버전(`ebaa707`) | 구버전(`retain_grad`, `2942f0f`) |
|---|---|---|
| 1500 | **22.23GB — 통과** | **OOM** (backward 직후 `a.grad[0].float()`에서 죽음) |
| 2000 | OOM (forward 단계에서 이미) | (테스트 안 함 — 의미 없음, 아래 참고) |

**T=1500은 travel(중앙값 1420)/workspace(중앙값 1378)의 실제 실패 구간과 정확히
겹친다.** "40% 메모리 절감"이라는 원래 목표보다 강한 결과를 얻었다 —
**같은 길이에서 OOM을 성공으로 뒤집는다.**

역산해보면 앞뒤가 맞는다: T=1500에서 forward만으로 이미 ~21.7GB (양쪽 공통).
구버전은 여기에 **28개 층의 grad를 전부** 더 얹어(+7.1GB, 문서 표와 일치) 28.8GB로
카드 용량(23.64GB)을 넘는다. 훅 버전은 한 층씩만 순간적으로 들고 바로 버려 +1GB
미만, 22.23GB로 통과.

**새로 발견한 한계 — T=2000은 태스크 A와 무관하게 forward 단계에서 이미 OOM이다.**
7B 4bit 모델 하나 로드 + attention 텐서 저장(28층×2000²×2바이트 ≈ 12.5GB) +
Q/K/V·MLP 등 나머지 activation만으로 forward 하나가 23GB를 넘는다. **태스크 A는
backward 단계만 줄이므로, forward 자체가 카드 용량을 넘는 길이에서는 도움이 안
된다.** 실제 AgentDojo `max_seq_len=2000` 필터로 들어오는 예시 중 T가 1500~2000
사이인 것들은 태스크 A로도 여전히 위험하다 — 다음 8/21 s3_7b 재실행에서 이 경계가
실제로 얼마나 넓은지 확인할 것 (아래 "다음").

**다음**: 태스크 A 반영 후 실제 8/21 s3_7b와 같은 조건(`head_n=200`,
`max_seq_len=2000`, `batch_size=5`)으로 AgentDojo discover-parallel을 재실행해
travel/workspace 생존율이 실제로 오르는지 확인 (진행 중 — 결과 나오면 이 절에 추가).

## 2. 다음 태스크 — 이 순서로

### 태스크 A. gradient 저장 제거 (backward 훅) — ✅ **완료 (2026-08-24, 1.3절 참고)**

위 표의 **절반**을 없앤다 (7B T=2000 기준 12.5GB → 6.3GB). 국소적 변경이고
**기존과 같은 숫자가 나오는지 검증할 수 있다.**

**대상**: `attn_relevance.py`의 `compute_head_relevance`

**현재 구조**:
```python
attn_maps = out.attentions
for a in attn_maps:
    if a.requires_grad:
        a.retain_grad()          # ← 모든 레이어의 grad를 backward 끝날 때까지 보관
target_logit.backward()
for l, a in enumerate(attn_maps):
    rel = _clamp_pos(a[0].float() * a.grad[0].float())
    group_scores[g][l] = rel[:, :, positions].sum(dim=(1, 2)).cpu()
```

**바꿀 구조**: `retain_grad()` 대신 `register_hook`. gradient가 계산되는 **그 순간**
`ReLU(a × grad)`를 span에 합산해 `[heads]` 벡터로 줄이고 CPU로 보낸 뒤, gradient는
바로 버린다.

```python
handles = []
for l, a in enumerate(attn_maps):
    if not a.requires_grad:
        continue

    def _make(l, a):
        def _hook(grad):
            rel = (a[0].detach().float() * grad[0].float()).clamp(min=0)
            for g, positions in key_spans.items():
                if positions:
                    group_scores[g][l] = rel[:, :, positions].sum(dim=(1, 2)).cpu()
            return None          # grad 수정 안 함 → 훅 끝나면 해제됨
        return _hook

    handles.append(a.register_hook(_make(l, a)))

target_logit.backward()
for h in handles:
    h.remove()
```

주의:
- **루프 변수 캡처**를 반드시 팩토리(`_make`)로 묶을 것. 안 그러면 모든 훅이 마지막
  `l`을 본다.
- `a[0].detach()` — `a` 자체는 autograd가 어차피 들고 있으므로 추가 메모리 없음.
- 훅이 안 불리는 레이어가 있을 수 있으니 `group_scores`는 0으로 초기화 유지.

**검증 (GPU 1장, 수 분)**:
```bash
# 1) 숫자가 같은지 — 0.5B에서 수정 전/후 비교
CUDA_VISIBLE_DEVICES=0 python run_pipeline.py \
  --model Qwen/Qwen2.5-0.5B-Instruct --family qwen2 --topk 20 --dataset_limit 3
# → results/2026-08-21_Qwen-Qwen2-5-0-5B-Instruct_bf16/summary.txt 와 jaccard 3개 대조
#   (기존 값: read,internal=0.212 / 나머지는 그 파일 참고)

# 2) 피크 메모리가 실제로 줄었는지
#    compute_head_relevance 호출 전후로 torch.cuda.max_memory_reserved() 출력해 비교
```

**성공 기준**: jaccard 값이 소수 셋째 자리까지 동일 + 피크 메모리 40% 이상 감소.
→ **둘 다 충족, 1.3절에 실측 기록.**

### 태스크 B. 32B를 GPU 3장에 분산 (`device_map="auto"`)

태스크 A를 해도 32B는 단일 카드에 안 들어간다. 64층을 3장에 나누면 레이어당 attention도
분산되므로 카드당 약 1/3이 된다.

**좋은 소식**: `compute_head_relevance`는 이미 레이어별로 `.cpu()`에 축약해 담으므로
**대체로 그대로 동작할 가능성이 높다.** (예전에 "device_map auto는 안 된다"고 적었던 것은
OOM 로깅이 device 0만 본다는 표시 문제였지 정확성 문제가 아니다.)

**손봐야 할 곳**:
1. `attn_relevance.load_model_for_relevance` — `device_map=device`로 고정돼 있다.
   `--device_map {auto,cuda}` 같은 인자를 추가하거나 `device="auto"`를 허용.
2. **`runtime_env.resolve_dtype`이 `str(device).startswith("cuda")`로 판정한다.**
   `device="auto"`를 넘기면 **fp32로 떨어진다** — 반드시 같이 고칠 것.
3. 입력 텐서는 첫 device(보통 `cuda:0`)에 있어야 한다. 데이터용 device와 모델
   `device_map`을 **분리해서** 받는 게 안전하다.
4. `compare_head_sources.py`의 OOM 로깅(`torch.cuda.memory_allocated()`)은 device 0만
   본다 — 표시만 부정확하니 급하지 않다.

**주의**: 3장을 다 쓰면 병렬 실행이 불가능하고 공용 서버에서 남이 못 쓴다.
`gpu_free`로 확인하고, 오래 걸리면 미리 알릴 것.

- 지시 1(suite 균등): 원인을 **두 겹** 규명했다. (a) 어댑터가 첫 턴만 봐서 travel이 8개로
  줄어 있었다 → 일반화로 59개. (b) 그래도 **OOM이 긴 suite를 골라 죽여** 균형이 다시
  깨진다(생존율 travel 18% vs slack 100%). 이건 방법론의 계산 비용 한계라는 결론.
- 지시 4(split): user_task 누수를 찾아 group split으로 고치고 평가까지 연결했다.
- 지시 2(스케일업): 32B가 안 되면 **"단일 24GB로는 메모리상 불가능, 3장 분산이 필요"**를
  근거(위 1.2 표)와 함께 보고. Llama-3.1-8B(패밀리 축)는 7B와 같은 비용이라 실행 가능.

즉 **태스크 A·B가 실패해도 발표 내용은 확보돼 있다.** 무리하지 말 것.

## 4. 확정된 사실 — 재검증 불필요

| 항목 | 결론 | 근거 |
|---|---|---|
| **dtype** | **bf16 고정** | fp16은 7B+AgentDojo에서 **20/20 NaN**. 0.5B 합성에서도 1/3. loss scaling으로 못 살림(scale 0.01/1/100에서 NaN 개수 동일 = forward overflow). bf16 에뮬레이션 오버헤드는 fp32 대비 +13% |
| **pair 수** | **307쌍** (기존 220 + 일반화 87) | travel 8→59. `never=0` — 주입은 항상 대화에 있다 |
| **길이 필터** | `max_seq_len` **상향은 무의미** | 2000→6000으로 올려도 207→209 |
| **OOM 원인** | **길이 의존.** 단편화 아님 | `expandable_segments`로 81/150 → 85/154 (비율 54%→55%, 무변화) |
| **`--batch_size`** | 5 이하 유지 | 16GB/batch5=105/150 vs 24GB/batch15=74/150 |
| **환경** | Miniforge+conda env(3.11), `PYTHONNOUSERSITE=1`, torchvision을 torch와 같은 인덱스에서 | `env.sh`, `run-guide.md` 부록 A |

## 5. 8/26 발표에서 **정정**할 것

1. **"travel은 OOM으로 제외됐다" → 절반만 맞다.** travel은 relevance 계산에 들어가기도
   전에 pair 생성 단계에서 140조합 중 8개로 줄어 있었다(어댑터가 첫 tool 턴만 봄).
   일반화로 59개까지 늘렸지만, **그다음에 OOM이 다시 9개로 줄인다.** 원인이 두 겹이었다.
2. **suite 불균형은 구조적이다.** workspace가 전조합의 59%(560/949)를 차지한다.
3. **`split_pairs`는 held-out이 아니었다.** pair 단위로만 나눠 같은 user_task가 양쪽에
   들어갔고, 프롬프트의 system/user 질문/history를 전부 공유했다.
