## 1. 오늘 있었던 일 — S6(Llama-3.1-8B) 스모크 3연전

`status-2026-08-25.md` 4절에서 예정했던 Llama-3.1-8B 스모크를 실제로 돌리면서 예상 못 한
문제를 만나고 고쳤다.

| 시도 | 조건 | 결과 |
|---|---|---|
| smoke1 | 단일 GPU, `max_seq_len=1200` | banking/slack **100% 성공**(12/12, 7/7), **travel/workspace 100% OOM**(8/8, 10/10) |
| smoke2 | 단일 GPU, `max_seq_len=800` | travel/workspace가 OOM 이전에 **길이 필터에서 아예 후보 풀 자체가 0**으로 사라짐(`[split]`에 두 suite가 안 나옴) — 더 낮춰도 소용없다는 뜻 |
| smoke3 | **2-GPU 분산**(`--device_map auto`), `max_seq_len=1200` | **`n_oom_skipped=0`, 4개 suite 전부 성공**(banking 12/slack 7/travel 8/workspace 10). layer 쏠림 없음(11~15층 중심 + 17·22 소수, layer 0 없음 — 32B 분산 버그 재발 안 함) |

**원인**: fp16 Llama-8B는 가중치가 ~16GB라 24GB 카드 1장에서 relevance 계산(backward) 여유가
~8GB뿐이었음(32B는 3장 분산이라 카드당 가중치가 오히려 적었고, 7B는 4bit라 5.7GB뿐이었어서
이 문제가 안 보였던 것). **"작은 모델이라 쉬울 것"이라는 가정이 틀렸다** — fp16 단일 카드가
오히려 헤드룸이 제일 빡빡한 조건이었음. 2-GPU 분산(`--device_map auto`)으로 카드당 가중치를
~8GB로 줄이니 해결됨.

**HF 게이트**: `meta-llama/Llama-3.1-8B-Instruct` 승인 완료(오늘 중) — unsloth 우회 재업로드는
더 안 씀, 다운받아뒀다면 정리 대상(`rm -rf "$HF_HOME/hub/models--unsloth--Meta-Llama-3.1-8B-Instruct"`).

## 2. S4 본실행 — launch 해둠, 결과 미확인

```bash
mkdir -p results/2026-08-25_s6_llama8b
CUDA_VISIBLE_DEVICES=0,1 python compare_head_sources.py discover-parallel \
  --source agentdojo \
  --model meta-llama/Llama-3.1-8B-Instruct --family llama \
  --device cuda:0 --device_map auto \
  --head_n 200 --max_seq_len 1200 --batch_size 5 \
  --out_json results/2026-08-25_s6_llama8b/heads_agentdojo.json
```

**다음 세션에서 확인할 것** (`results/2026-08-25_s6_llama8b/heads_agentdojo.json`):
- `n_oom_skipped`/`n_nan_skipped` — 0에 가까운지
- top-20(또는 topk) head의 layer 분포 — layer 0 쏠림 없는지(스모크에서는 11~15층 중심이었음,
  본실행도 비슷한 패턴이면 정상)
- **`split_info.per_stratum.travel.shortfall`** — **거의 확실히 발생함.** 이 길이 필터
  (`max_seq_len=1200`)에서 travel 후보 풀 자체가 작아서(스모크에서 `n_groups=4`) quota=50까지
  못 채울 가능성이 높다. 32B S4 때 travel이 겪은 것과 같은 패턴 — **재조정 없이 그대로 진행하고
  결과에 caveat만 남길 것** (`status-2026-08-24.md` 2.2절과 같은 처리 방식).

## 3. S4 확인 끝나면 바로 — S5(eval)

```bash
CUDA_VISIBLE_DEVICES=0,1 python run_agentdojo_eval.py \
  --model meta-llama/Llama-3.1-8B-Instruct --family llama \
  --device cuda:0 --device_map auto \
  --heads_json results/2026-08-25_s6_llama8b/heads_agentdojo.json \
  --eval_split heldout --limit_pairs 15 \
  --out_json results/2026-08-25_s6_llama8b/agentdojo_eval.json
```

`--suite`를 따로 지정하지 않으면 4개 다 시도 — travel이 S4에서 shortfall 나더라도(2절)
eval(S5)의 heldout 후보 풀은 별개 경로라 자동으로 0건이 되는 건 아님(`status-2026-08-25.md`
1.5절에서 32B도 같은 이유로 travel eval이 정상 나왔음). 결과 나오면 k=0 vs k=N utility/security,
`parse_stats`(tool_call 파싱 실패율)를 32B 결과(`status-2026-08-25.md` 1·2절)와 나란히 놓고
비교할 것 — 특히 baseline utility가 Qwen2.5-7B/32B보다 낮게 나올 가능성 있음(BFCL 벤치마크상
Llama-3.1-8B의 function calling 점수가 Qwen2.5-7B보다 낮음, 같은 대화에서 확인) — 그 경우
utility 낮음 자체가 "패밀리 차이"인지 "이 모델의 원래 tool-calling 실력"인지 구분해서 서술할 것.
