## 5. S6 eval(Track B) 실행 결과 — `results/2026-08-25_s6_llama8b/agentdojo_eval.json`

### 5.1 tool_call 파싱 성공률 0% — Qwen 전용 포맷을 family 무관하게 하드코딩한 버그

```
parse_stats: n_calls=90  ok=0  no_tag=90  truncated=0  json_errors=0
```

90/90(100%) `no_tag` — Qwen 32B/7B에서 봤던 "가끔 실패"(29~32%)가 아니라 **단 한 번도
성공 못 함**. 모든 row에서 `k0_utility==kN_utility`, `k0_security==kN_security`가 완전히
같다(예: banking 15쌍 전부) — knockout을 켜든 끄든 모델이 tool을 아예 안 쓰니 차이가
날 수가 없다. **즉 `kN_security_rate=0.0`은 방어가 작동한 게 아니라 애초에 공격이 시도될
기회(tool 호출)가 없었다는 뜻이다.**

**원인**: `adapters/agentdojo_pipeline.py:36`
```python
_TOOL_CALL_RE = re.compile(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", re.DOTALL)
```
이 태그가 **family 무관하게 하드코딩**돼 있다. 이 관례는 애초에 **Qwen2.5 전용**이다
— Qwen2.5 tokenizer의 `chat_template`(Jinja) 자체가 "함수 호출은 `<tool_call>` XML
태그로 감싸라"는 지시문을 템플릿 안에 박아넣고 있다(어댑터 파일 상단 docstring의
"Qwen2.5는 `<tool_call>` 포맷으로 파인튜닝돼 있어 그 포맷을 그대로 쓰는 게 안정적"이라는
근거가 바로 이거다). `_render_prompt`는 `self.tok.apply_chat_template(...)`을 쓰는데
S6에서는 `self.tok`가 **Llama 토크나이저**라서 Llama 자체 템플릿이 렌더링되고, **Llama
3.1 공식 템플릿은 이 `<tool_call>` 관례를 쓰지 않는다** — 모델에게 애초에 그 포맷으로
답하라고 지시한 적이 없는데 파서만 그 포맷을 기다리고 있었다.

`--family llama`는 지금까지 `attn_relevance.py`(LRP relevance 계산)에만 연결돼 있었고
tool-call 파싱 쪽엔 한 번도 연결된 적이 없었다 — S6 전까지는 전부 Qwen 계열만 돌려서
이 gap이 드러나지 않았을 뿐이다.

### 5.5 2차 재실행 결과 — 파싱은 크게 개선됐지만 2차(경미한) 버그 하나 더 발견·수정

서버에서 위 커맨드를 커밋 `bf78653`로 이미 재실행함(`env.timestamp=2026-08-26T02:21:29Z`,
`env.git.dirty=false`). 결과를 이 세션에서 받아 확인함.

**파싱 성공률 0% → 79.1%로 개선 확인**:
```
parse_stats: n_calls=311  ok=246(79.1%)  no_tag=36(11.6%)  truncated=7(2.3%)  json_errors=22(7.1%)
```
Qwen 기준선(68~71%)보다 오히려 **더 높다** — 파싱 자체는 정상 작동한다는 뜻.

**처음으로 진짜 knockout 신호가 나타남**: slack suite `k0_security=13.3%(2/15) →
kN_security=0%(0/15)` — 공격 2건이 knockout 후 둘 다 실패로 전환. utility는 두 조건에서
동일(banking 0.4/0.4, slack 0.533/0.533)하게 유지 — 32B/7B에서 봤던 패턴(공격 억제 +
정상 기능 보존)과 방향이 일치하는 **첫 유효 Llama 결과.**

**그런데 `json_errors=22`(7.1%)가 예상보다 높아 `truncated_examples`(5건)를 직접 검토함.**
전부 이런 형태였다:
```
The function call {"name": "get_most_recent_transactions", "parameters": {"n": "1"}}
returns the most recent transaction, ... The amount of this transaction is 10.0.
```
이건 **완결된 유효 JSON 뒤에 모델이 자연어 설명을 덧붙인 것**뿐인데, 5.4에서 짠
`has_close = completion.strip().endswith("}")` 조건이 "문자열 전체가 `}`로 끝나야
완결"로 너무 엄격하게 판정해서 — 유효한 tool call인데도 `truncated`로 잘못 분류되고
**파싱 시도조차 안 하고 버려지고 있었다.** Qwen 원본 로직(닫는 태그 유무)을 그대로
흉내내려다, Llama는 태그가 없다는 차이를 놓친 것.

**수정 (커밋 `bd19216`)**: 판정 기준을 "completion 전체 끝맺음"이 아니라 **추출한 JSON
스팬의 중괄호 개수 균형**으로 바꿈 — `_extract_json_object`가 첫 `{`~마지막 `}` 사이를
뽑으므로, 진짜로 `max_new_tokens`에 잘렸으면 중괄호 개수가 안 맞을 가능성이 높고, 뒤에
붙는 자연어 설명 자체는 중괄호를 안 쓰므로 이 판정에 영향이 없다. 실제 `truncated_examples`
5건으로 로컬 검증(의존성 없는 순수 함수 재현) — **전부 정상 파싱됨**을 확인.

**⚠️ 3차 재실행 필요**: 이 수정은 아직 서버에서 실행 검증 전이다. `json_errors` 22건 중
몇 건이 이 버그로 인한 오분류였는지(즉 3차 재실행 후 `ok`가 79.1%에서 얼마나 더 오르는지)
확인해야 최종 수치를 신뢰할 수 있다. 특히 이번에 나온 slack security 신호(13.3%→0%)가
3차에서도 유지되는지가 핵심 확인 사항 — n이 작아(15쌍) 몇 건의 재분류만으로도 비율이
바뀔 수 있다.

### 5.6 3차 재실행 결과 (최종) — travel OOM 해결, 대신 새 파서 한계 발견

3차 재실행은 두 가지를 동시에 반영했다: 코드는 `bd19216`(5.5절 truncated 판정 수정),
실행 옵션은 `--device_map auto`를 2-GPU로 제한(`CUDA_VISIBLE_DEVICES=0,1`) — travel
suite에서 OOM이 잦다는 관측(사용자 보고)에 대응한 것. 8B는 fp16 ~16GB로 24GB 카드 1장에
가까스로 들어가는 크기라, travel의 긴 tool 응답이 eager attention prefill 메모리를
밀어붙인 것으로 추정. 2장 분산으로 카드당 가중치 footprint를 절반(~8GB)으로 줄여
activation 여유를 확보.

**결과** (`env.git.commit=7b221f8`, dirty:false, `env.gpus`에 카드 2장만 찍힘 —
`CUDA_VISIBLE_DEVICES=0,1` 제한이 의도대로 적용됨 확인):

```
parse_stats: n_calls=380  ok=283(74.5%)  no_tag=45(11.8%)  truncated=2(0.5%)  json_errors=50(13.2%)
```

**travel OOM은 해결됨** — `travel.n_pairs`가 지난 2차의 `0` → 이번엔 `15`(15/15 전부
평가 완료). 다만 **travel의 utility·security가 15쌍 전부 0%로 나왔다** — 이건 실제
모델 성능이 아니라 **새로운 파서 한계다.** `truncated_examples`에서 확인:

```
...{"name": "get_hotels_prices", "parameters": {...}}; {"name": "get_hotels_address",
"parameters": {...}}; {"name": "create_calendar_event", "parameters": {...}}
```

Llama가 **한 턴에 여러 tool call을 세미콜론(`;`)으로 이어붙여 응답**하는 패턴을
travel에서만 쓴다(banking/slack/workspace에서는 관측 안 됨 — 여행 예약처럼 여러 단계
호출이 자연스러운 태스크 특성으로 보임). `_extract_json_object`(첫 `{`~마지막 `}`)는
"한 턴에 JSON 객체 하나"를 가정하므로 이 경우 여러 객체+세미콜론이 통째로 잡혀
`json.loads`가 실패한다 — `json_errors`가 2차 22건 → 3차 50건으로 늘어난 게 이 때문
(2차는 travel이 OOM으로 아예 평가에 안 들어가서 이 실패 모드가 안 보였을 뿐).
**travel 15쌍은 tool 실행 자체가 안 돼 utility/security가 구조적으로 0이 됐다 —
"Llama가 travel을 못 푼다"거나 "knockout이 travel에서 효과가 없다"는 결론이 아니다.**

**banking/slack/workspace(n=44, travel 제외)는 유효하다 — 최종 발표용 수치**:

| suite | n | k0 utility | kN utility | k0 security | kN security |
|---|---|---|---|---|---|
| banking | 15 | 40.0% | 40.0% | 0% | 0% |
| slack | 15 | 53.3% | 53.3% | **13.3%** | **0%** |
| workspace | 14 | 21.4% | 21.4% | 0% | 0% |
| **합계** | **44** | **38.6%** | **38.6%** | **4.5%** | **0%** |

**utility 완전 유지(38.6%→38.6%) + security 완전 억제(4.5%→0%)** — 32B/7B에서 확립된
"knockout이 공격은 죽이고 정상 기능은 보존한다"는 패턴이 **Llama family에서도 재현됨**.
발표에 쓸 수 있는 첫 유효 패밀리 축(S6) 결과다.

**travel 파서 한계는 지금 더 고치지 않기로 함(발표 당일 판단)**: (1) 시간이 촉박하고,
(2) banking/slack/workspace 3개 suite만으로 지시 2번(패밀리 축)에 충분히 답이 되고,
(3) 세미콜론 구분자가 모델이 즉흥적으로 만든 비표준 포맷이라 안전하게 파싱하려면
추가 검증이 필요함. **발표 문구**: "travel은 멀티 tool-call 체이닝 파서 미지원으로
0%(실제 결과 아님, caveat)" — 후속 과제는 `docs/todo.md` 참고.
