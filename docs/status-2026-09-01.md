## 1. 이번 세션(2026-08-31~09-01) 요약

**P16(교수님 피드백 4번 — tool-call 파서를 AgentDojo 기본값으로) 완료.** Track B
(`run_agentdojo_eval.py`)가 쓰던 tool-call 프롬프트/파서가 AgentDojo 자체 기본값이
아니라 우리가 만든 커스텀 파서였음이 드러남(1.5B가 기본값을 안 따라서 대체했었음).
`--tool_call_format agentdojo_default` 옵션 추가(AgentDojo 자체 `_make_system_prompt`/
`_parse_model_output` 재사용) 후 Qwen2.5-7B·Llama-3.1-8B A/B 비교 → **결론: banking/
workspace 저조는 파서 아티팩트가 아니었고(확인 완료), 1.5B의 AgentDojo 기본 포맷 실패
전례는 8B에서 재현 안 됨(parse ok율 거의 동일) → `agentdojo_default`를 기본값으로
채택.** 상세: `feedback-2026-08-31.md` 1~2.5.3절.

**P15(ASB 데이터셋 전환) 어댑터는 구현 완료했지만 교수님 지시로 보류.** 교수님이
스케일업 → 표본 확대 → 최적 k 탐색(다른 아키텍처/ASB는 후순위) 순서를 지시해서 그대로
따르기로 함 — `adapters/asb.py`는 남아있으니 필요해지면 바로 재개 가능.

**서버 이전 대응(aisec-king)**: GPU가 RTX PRO 4500 32GB → +RTX A6000 48GB → +RTX 4090
24GB로 3장까지 늘어남(같은 날 중 두 번 추가됨). `env.sh`가 bash 전용이던 걸 zsh도
지원하도록 수정, `$JB`를 하드코딩 경로 대신 저장소 자기 위치 자동 감지로 변경. 상세:
`docs/run-guide.md` 부록 B.

**코드리뷰(2026-08-31, high)로 실버그 다수 수정**: qwen3 head-discovery 경로 미배선,
Qwen3 thinking mode 미차단(P13과 같은 종류의 조용한 실패), ASB `limit`이 단일 agent로
쏠리던 문제, env.sh의 `$BASH_SOURCE` 미가드 등. 전부 커밋·검증 완료.

**스케일업(Qwen2.5-32B) + 표본 확대 — 이번 세션의 핵심 실험 라인**:
- 32B vs 7B 비교(초기 n=43~45): 스케일업해도 ASR 안 오름(6.7%→4.7%) — 재확인
- slack/travel만 재실행: "slack만 파싱 실패 많다"는 의혹 기각(slack 73.6% vs travel
  86.4% parse_ok). travel이 agentdojo_default에서 정상 작동(Qwen 기준)
- **4 suite 전부 held-out 풀 최대치로 확대(n=148, banking/slack/travel 풀 전부)**:
  스케일업 결론 최종 확정(ASR 6.8%). **slack에서 knockout이 성공 공격 8건 중 5건
  (62.5%)을 못 막음** — banking/travel/workspace는 여전히 완벽 억제(0%)
- **원인 확정**: `agentdojo` 패키지의 slack injection task 정의를 직접 열어본 결과,
  성공한 8건 전부가 `injection_task_1/3/5`(1~3 tool call, 단순 인자)였고
  `injection_task_2/4`(다단계+문자열 concat, 6개/2개 tool call)는 전무. **"문구가
  설득력 있어서"가 아니라 "실행에 필요한 tool call 개수가 적을수록 knockout으로
  injection 신호를 줄여도 우연히 실행되기 쉽다"**는 쪽으로 원인이 좁혀짐. 상세:
  `feedback-2026-08-31.md` 2.1.1~2.1.4절.

**`tool_knowledge` 공격 재검토 결정**: 2026-07-31에 이미 한 번 시도된 적 있음
(`docs/todo.md` 572행 근방) — 그때 결론은 "가설 기각, ASR 거의 그대로(0.022 vs
0.021)"였지만, (a) 7B·구형 파서·n=46로 지금보다 훨씬 작은 세팅이었고 (b) **injection_task별
분해를 안 봤음**. `tool_knowledge`(`agentdojo.attacks.important_instructions_attacks.
ToolKnowledgeAttack`) 실제 코드를 열어보니, `injection_task.ground_truth()`에서 뽑은
**정확한 tool 이름+인자 시퀀스를 문구에 통째로 박아 넣어** 실행 난이도를 낮추는
공격임을 확인 — 오늘 발견한 "복잡도가 문제" 가설과 정확히 맞아떨어지는 검증 도구.
지금 세팅(32B, agentdojo_default, 확대 표본)으로 재실행 중. 상세: `feedback-2026-08-31.md`
맨 아래(2026-09-01 추가분).

## 2. 두 결과 확인 시 볼 것

### 2.1 Llama-3.1-8B 확대 결과 (`llama8b_agentdojo_default_expanded.json`)

**목적**: Qwen 32B에서 발견한 "slack knockout 실패(62.5%)" 패턴이 Llama에서도
재현되는지 — 재현되면 일반적 현상(모델 무관), 안 되면 Qwen-32B(또는 32B 스케일)
특유의 현상.

**볼 것**:
- `per_suite.slack.k0_security_rate` vs `kN_security_rate` — 격차가 크면(=억제 실패
  많으면) 패턴 재현
- `rows`에서 slack suite만 필터링해 성공(`k0_security=true`)한 쌍들의 `injection_task`가
  `injection_task_1/3/5`에 몰려있는지, `2/4`는 없는지 — Qwen과 같은 패턴인지 확인
- Llama의 heads_json은 `results/2026-08-25_s6_llama8b/heads_agentdojo.json` (banking/
  slack 풀 전부=45/35, travel/workspace는 45로 제한된 표본 — Qwen과 동일 조건으로
  비교 가능)

### 2.2 Qwen 32B tool_knowledge 결과 (`qwen32b_agentdojo_default_toolknowledge.json`)

**목적**: "실행 난이도가 병목"이라는 가설의 직접 검증 — `injection_task_2/4`(복잡,
`important_instructions`에서 0% 성공)가 `tool_knowledge`(정답 시퀀스를 통째로 알려줌)
에서는 성공률이 오르는지.

**볼 것**:
- `rows`에서 각 suite별로 `injection_task`별 `k0_security` 성공률 breakdown 계산
  (지금 코드엔 injection_task별 집계가 없으니 직접 스크립트로 뽑아야 함 —
  `tools/` 밑에 새로 만들 수도 있음)
- **핵심 질문**: slack의 `injection_task_2`/`4` k0_security_rate가 0%에서 벗어났는가?
  전체 ASR 자체가 2026-07-31처럼 "거의 그대로"인지, 아니면 injection_task 분해에서
  실제로는 크게 갈리는지가 이번 재검증의 핵심.
- `parse_stats`도 같이 볼 것 — `tool_knowledge`는 프롬프트가 더 길어져서(tool 시퀀스
  텍스트 추가) parse_ok율이 `important_instructions`보다 떨어질 가능성 있음.
- ⚠️ `ToolKnowledgeAttack.get_tools_sequence()`가 `placeholder_args`가 없는 tool call을
  만나면 `ValueError`를 던진다 — `run_agentdojo_eval.py`의 try/except가 그 쌍만 건너뛰므로
  `n_pairs`가 148보다 좀 적게 나올 수 있음(정상, `docs/todo.md` 593행 근방에 이미
  기록된 전례와 같은 종류).

## 3. 결과에 따른 분기

- **둘 다 가설 지지** (Llama도 slack 패턴 재현 + tool_knowledge에서 2/4 성공률 상승):
  "knockout의 진짜 약점은 injection 억제가 아니라 실행 복잡도가 낮은 공격에 대한
  우연한 leak"이라는 결론이 꽤 단단해짐 — k-sweep(2.2절, 지금까지 후순위였던 항목)을
  이 가설 검증용으로 재우선순위화할 가치 생김(head를 더 늘리면 이 leak이 줄어드는지
  보는 것).
- **Llama는 slack 패턴 재현 안 됨**: Qwen 또는 32B 스케일 특유의 현상 — Llama 32B급
  스케일(70B, P12)이나 Qwen 다른 스케일(7B로 같은 확대 표본 재확인)로 축을 좁혀야 함.
- **tool_knowledge에서도 2/4가 여전히 0%**: "실행 난이도" 가설 기각 — 2026-07-31과
  같은 결론이 지금 세팅에서도 재확인되는 것이므로, 다른 설명(예: 이 두 injection_task
  자체가 AgentDojo 채점 기준상 더 엄격한 성공 조건을 가졌을 가능성 — `injection_tasks.py`
  의 `security()` 정의를 다시 볼 것)을 찾아야 함.
