## 1. 이번 세션(2026-08-31~09-01) 요약

**P16(교수님 피드백 4번 — tool-call 파서를 AgentDojo 기본값으로) 완료.** Track B
(`run_agentdojo_eval.py`)가 쓰던 tool-call 프롬프트/파서가 AgentDojo 자체 기본값이
아니라 우리가 만든 커스텀 파서였음이 드러남(1.5B가 기본값을 안 따라서 대체했었음).
`--tool_call_format agentdojo_default` 옵션 추가(AgentDojo 자체 `_make_system_prompt`/
`_parse_model_output` 재사용) 후 Qwen2.5-7B·Llama-3.1-8B A/B 비교 → **결론: banking/
workspace 저조는 파서 아티팩트가 아니었고(확인 완료), 1.5B의 AgentDojo 기본 포맷 실패
전례는 8B에서 재현 안 됨(parse ok율 거의 동일) → `agentdojo_default`를 기본값으로
채택.** 상세: `feedback-2026-08-31.md` 1~2.5.3절.

**P15(ASB 데이터셋 전환) 어댑터는 구현 완료했지만 교수님 지시로 보류.** 교수님이
스케일업 → 표본 확대 → 최적 k 탐색(다른 아키텍처/ASB는 후순위) 순서를 지시해서 그대로
따르기로 함 — `adapters/asb.py`는 남아있으니 필요해지면 바로 재개 가능.

**서버 이전 대응(aisec-king)**: GPU가 RTX PRO 4500 32GB → +RTX A6000 48GB → +RTX 4090
24GB로 3장까지 늘어남(같은 날 중 두 번 추가됨). `env.sh`가 bash 전용이던 걸 zsh도
지원하도록 수정, `$JB`를 하드코딩 경로 대신 저장소 자기 위치 자동 감지로 변경. 상세:

**코드리뷰(2026-08-31, high)로 실버그 다수 수정**: qwen3 head-discovery 경로 미배선,

쏠리던 문제, env.sh의 `$BASH_SOURCE` 미가드 등. 전부 커밋·검증 완료.

**스케일업(Qwen2.5-32B) + 표본 확대 — 이번 세션의 핵심 실험 라인**:
- 32B vs 7B 비교(초기 n=43~45): 스케일업해도 ASR 안 오름(6.7%→4.7%) — 재확인

  스케일업 결론 최종 확정(ASR 6.8%). **slack에서 knockout이 성공 공격 8건 중 5건

- **원인 확정**: `agentdojo` 패키지의 slack injection task 정의를 직접 열어본 결과,

  `injection_task_2/4`(다단계+문자열 concat, 6개/2개 tool call)는 전무. **"문구가

  injection 신호를 줄여도 우연히 실행되기 쉽다"**는 쪽으로 원인이 좁혀짐. 상세:

## 3. 결과 (2026-09-01 확정) 및 다음에 할 일

**결론: 2.1.4 "실행 복잡도 낮은 공격의 우연한 leak" 가설 폐기.** 근거 3개(feedback
2.1.5·2.1.6·2.1.9):

1. **slack knockout 불안정은 모델 무관도 Qwen 계열 특유도 아님** — Llama-3.1-8B
   (2.1.5), Qwen2.5-7B(2.1.9) 둘 다 **bf16**에서 slack 성공을 knockout이 전량 억제
   (kN_sec 0/35). slack에서 knockout이 실패한 건 `qwen32b_agentdojo_default*` 실행이
   유일.
2. **injection_task_2/4의 0%는 실행 난이도가 아니라 `security()` 연언 채점 때문**(2.1.8:
   task_2 = 5키워드 4채널 전부 + 6스텝, task_4 = 3키워드 + concat → near-unwinnable).
   `tool_knowledge`로 정답 시퀀스를 줘도 2/4는 0%(2.1.6). → slack knockout 논의는
   `injection_task_1/3/5`(≤3 단순 call)로 좁혀짐.
3. **🔑 4bit 교란**: slack knockout이 실패한 유일한 실행(`qwen32b`)이 **유일하게
   `--four_bit`(4bit 평가)**. 두 8B급은 bf16. 따라서 "slack knockout 불안정"의 원인이
   **(1) 32B 스케일 / (2) 4bit 양자화**로 공변 — 지금 데이터로는 못 가른다.

**남은 사실**: *"`qwen32b_agentdojo_default`(4bit) 실행에서만 slack의 달성 가능한
단순 공격(injection_task_1/3/5)에 대해 knockout이 불안정했다"* — 원인 미확정.

**부분 근거 추가 (2026-09-01, feedback 2.1.11~2.1.12)**: 32B **bf16**을 돌려봤으나
OOM 대량 발생(`device_map auto`가 최소 카드 PRO4500에 몰고 `--device cuda:0`도 거기)
— slack 23/35만 완주. 그 열화 표본에서도 **bf16 knockout leak 1건 + backfire 1건**
(8B bf16은 둘 다 0). → **"32B 스케일" 쪽 정황**(약함). 확정은 아래 (d)로.

**다음에 할 일**:
- **(d) ← 지금 할 일 — 확정용, 가볍고 OOM 없음**: Qwen2.5-7B **`--four_bit`**, 같은
  확대 표본. 7B-4bit가 **깨끗**(slack kN_sec 0, backfire 0)이면 → 4bit 무죄, **32B
  스케일 확정**. 7B-4bit도 **불안정**이면 → 2.1.11 정황과 충돌, 14B-4bit로 재검토.
