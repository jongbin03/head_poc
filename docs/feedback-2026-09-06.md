### 1.2 "앞쪽 레이어에 헤드가 몰리는 현상" — 우리 프로젝트에도 이미 있다

교수님이 말한 현상은 우리 데이터에서 **layer 0 지배**로 계속 관측돼 온 것이다:

- `review-2026-07-29.md` §3-4: 1.5B `control_heads_both` 14개 중 **6개가 layer 0**
  (layer 0은 헤드가 12개뿐 → 절반이 차단됨). 7B는 15개 중 4개(layer당 28개라 비중 낮음).
- 3소스 비교(2026-07-31, 1.5B)에서 **3소스 교집합 5개가 전부 layer 0**: `(0,1)(0,3)(0,6)(0,7)(0,10)`.
- 14B(2026-07-31): 13개 중 4개가 layer 0 + layer 36에 인접 헤드 3개 클러스터(신규 패턴).
- lxt README가 **Qwen3**에 대해 "Attribution skewed toward first token"(🧪)을 명시 경고 —
  우리는 relevance를 D_inj span에 **합산**하므로 질량이 position 0에 흡수되면 점수가
  계통적으로 눌린다 (`plan-2026-08-26.md` §3.1.1).

**해석 쟁점** (review §3-4): layer 0 attention을 절반 막는 것은 "instruction-following
회로 차단"보다 **"초기 정보 대역폭 차단"**에 가까울 수 있다 — "우리가 고른 헤드가
특별하다"에 대한 가장 강한 대안 가설. 교수님 말대로 **헤드를 차단하는 게 아니라
평가만 진행**하는 것은 이 교란과 무관하게 유효하므로, 앞쪽 레이어 쏠림이 있는 모델도
그냥 돌려서 결과를 보는 게 맞다. 다만:

- **Qwen3-8B는 진단이 먼저** — `diag_qwen3_relevance.py`로 qwen2와 나란히 position별
  relevance 분포를 찍어, Qwen3가 baseline(qwen2) 대비 **유의미하게 더** 쏠리는지 확인.
  (attention sink는 causal LM 일반 현상이라 "0이 아님"이 아니라 "더 심함"이 기준.)
- **Llama-70B는 스케일 축 순수 대조** — Llama family 안에서 8B→70B, Qwen2.5 7B→32B에
  대응. 32B에서 나온 "스케일업 시 slack 공격 억제가 무너진다"는 반례가 Llama에서도
  재현되는지가 검증 포인트.

### 1.3 착수 순서 (권장)

1. **Llama-70B 먼저** — 진단 선행이 필요 없고(같은 lxt qwen2/llama 경로는 실측 완료),
   스케일 축 서사가 발표에 바로 붙는다. 단 P13(llama 파서) 서버 재검증 → 소규모 스모크로
   OOM/수율 확인 → A6000 48GB 단일 카드 우선. (`docs/todo.md` P12 "할 일" 4단계)
2. **Qwen3-8B는 진단 통과 후** — `diag_qwen3_relevance.py` 결과가 "qwen2와 큰 차이 없음"
   이면 그대로 진행, "훨씬 쏠림"이면 첫 토큰 제외 정규화를 먼저 설계.

### 2.3 재실행 설계 (착수 시, P4 §3·§5 연장)

- **탐색**: 서버에서 `compare_head_sources.py discover --source synthetic` +
  `discover-parallel --source agentdojo`를 **같은 모델(우선 Qwen2.5-7B, 다음 32B)**로
  나란히. 32B는 `discover-parallel`, `--batch_size` 작게(수율 좌우, P4 참고).
- **겹침**: `compare_head_sources.py compare` — jaccard / 우연 기준선 / 합집합 / 교집합,
  **layer 분포를 반드시 같이 출력**(layer 0 지배 재확인이 핵심).
- **전이 평가**: `run_agentdojo_eval.py`로 (a) synthetic 헤드, (b) AgentDojo 헤드,
  (c) 교집합, (d) 합집합 각각을 **`--tool_call_format agentdojo_default` + `nf4`+dq +
  held-out 풀 최대치**로 knockout 비교. slack은 held-out 35쌍 전수라 표본이 안정적.
- **layer-0-only 대조**: 교집합(전부 layer 0)만 knockout했을 때 효과 → "초기 정보
  대역폭 차단" 대안 가설 판별(review §3-4가 "다음 단계에서 반드시 보라"고 지목).

> "합성 헤드로 AgentDojo 평가"는 2026-07~08에 3번 했고, 방향은 일치(knockout이 공격을

## 3. Track A 헤드 탐색의 양자화 영향 — bf16 vs 4bit 대조 (미실행, 나중에)

**동기 (2026-09-08 논의)**: 70B를 어떻게 돌릴지 얘기하다 나온 갈래. 현재 Track A 헤드가
모델마다 양자화 조건이 다르다는 걸 확인:

| 모델 | Track A 탐색 | 양자화 | heads_json |
|---|---|---|---|
| Qwen2.5-7B | `--four_bit` | **fp4** (bnb 기본값, dq off) | `results/2026-08-24_s3_7b_taskA/heads_agentdojo.json` |
| Qwen2.5-32B | `--four_bit` | **fp4** | `results/2026-08-24_s4_32b/heads_agentdojo.json` |
| Llama-3.1-8B | 없음 | **bf16 풀정밀도** | `results/2026-08-25_s6_llama8b/heads_agentdojo.json` |

- `attn_relevance.py`의 4bit 경로는 `load_in_4bit=True, bnb_4bit_compute_dtype`만 지정 —
  `quant_type`/`double_quant` 미배선이라 **First Commit부터 fp4/no-dq 고정** (git 확인).
  `run_agentdojo_eval.py`는 P16(2.1.14)에서 nf4+dq로 교체됐지만 `attn_relevance.py`는 안 됨.
- P16 feedback **2.1.13·2.1.14**: fp4가 7B knockout *평가*를 과손상(backfire·utility 붕괴),
  nf4+dq로 대부분 해소. **탐색(discovery)에도 같은 왜곡이 있는지는 확인 안 됨** — 탐색은
  head *순위* 기반이라 knockout *궤적*보다 견고할 수 있으나, fp4 왜곡이 top-k 경계를
  흔들면 뽑히는 헤드 집합 자체가 달라질 수 있다.

**확인할 질문**: 같은 모델·같은 데이터로 Track A를 **bf16 vs fp4 vs nf4dq**로 각각 돌리면
헤드 집합이 유의하게 달라지는가? layer 분포(특히 layer 0 비중)는 바뀌는가?

**설계**:
1. **가장 싼 대조 = Llama-3.1-8B** — bf16 헤드가 이미 있음. `--four_bit`(fp4)로 동일
   조건 재실행(`--head_n 200 --max_seq_len 1200 --batch_size 5 --seed 42`, device_map은
   단일 카드로 — 8B nf4는 4090에 들어감) 후 `compare_head_sources.py compare`로 bf16 ↔
   fp4 jaccard·layer 분포 비교. nf4dq 배선(아래 3번) 후 3자 비교로 확장.
2. **7B 대조** — 7B bf16(~15GB)은 4090/A6000 단일 카드에 들어감. fp4 헤드 이미 있으니
   bf16만 추가로. 32B bf16(~65GB)은 A6000+PRO4500 device_map 필요, 느림 — 후순위.
3. **선행: `attn_relevance.py`에 nf4+dq 배선** (~5줄, `run_agentdojo_eval.py`와 동일하게
   `bnb_quant_type`/`bnb_double_quant` 인자 + `BitsAndBytesConfig`에 전달).
   `compare_head_sources.py`에도 같은 인자 노출.

**⚠️ 교란 통제 — OOM 스킵**: 4bit는 OOM이 적고 bf16은 많다(Llama-8B 149/200, 32B fp4
130/206). 처리된 pair 집합이 갈리면 헤드 차이가 "양자화 때문"인지 "표본 때문"인지 안
갈린다. **두 조건이 공통으로 완주한 pair로 제한**해서 비교하거나, `--max_seq_len`을
낮춰 양쪽 다 OOM 0이 되는 범위에서 돌릴 것.

**의의**: (a) 현재 32B 헤드(fp4 탐색)를 계속 써도 되는지 정당화, (b) 70B Track A를 4bit로
돌릴 때 헤드 신뢰도 근거, (c) feedback §1.3의 "Llama 8B(bf16) vs 70B(4bit) 정밀도 축
혼입" caveat을 정량화.
