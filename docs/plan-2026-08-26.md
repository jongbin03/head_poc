### 0.1 이번 사이클의 줄기 — 모델 2개로 같은 실험을 반복한다

**서사를 하나로 단순화한다:** 서버를 세우고 → **스케일을 키운 모델**로 **AgentDojo에서
직접 헤드를 찾고** → **split한 평가셋으로 바로 검증**하고 → 결과를 확인한 뒤
**모델을 바꿔서(Llama-3.1-8B) 똑같이 반복**한다. 이 한 줄기로 교수님 지시 4개 중 1·2·4가
전부 덮인다(3은 위 결정대로 예비 결과 보고).

```
서버 셋업 ─▶ [7B 스모크] ─▶ Qwen2.5-32B 4bit ─▶ AgentDojo 헤드 탐색 ─▶ 검증
                                                          │
                                            같은 절차 반복 ▼
                                                  Llama-3.1-8B
```

세부 단계는 [6절](#6-실행-순서). 이 줄기를 확정하면서 **원래 계획에서 두 가지를 바꿨다:**

#### (a) "27B" → **Qwen2.5-32B 4bit**

교수님 메모의 "27B"는 Gemma-3-27B를 가리키는데, **하필 AgentDojo와 최악의 조합이다.**
Gemma 3는 대부분 레이어가 sliding-window local attention이라, AgentDojo의 긴 tool
응답(최대 ~9600 토큰)에서 **D_inj span이 윈도우 밖으로 나가면 그 레이어 head의 relevance가
구조적으로 0**이 된다. 헤드를 못 찾는 게 아니라 **찾은 결과를 믿을 수 없게 된다.**
거기에 멀티모달 래퍼 + 게이트 모델 + lxt/transformers 4.51.3 조합 미검증까지 붙는다
([3.1.2절](#312-gemma-3-27b--lxt는-되지만-다른-제약-3개)).

**Qwen2.5-32B 4bit은 27B보다 크면서 코드 수정이 0이다.** "모델 스케일 키우기"라는 지시를
더 잘 만족하고 지뢰가 없다. 발표에서는 "27B급 이상(32B)"으로 보고하면 된다.

#### (b) 32B 직행 전에 **7B 스모크 1회**를 게이트로 넣는다

현재 AgentDojo 헤드 탐색 수율이 **150번 중 18번 성공**으로 기록돼 있다
([4.2절](#42-원인-2--compute_head_relevance의-프로세스-전역-메모리-누수)). 32B는 64층 ×
64헤드라 attention 텐서가 7B의 4~5배다. **바로 32B로 가면 쓸 만한 표본이 거의 안 남을
위험이 크다.**

7B 스모크는 코드 작업이 아니라 **기존 코드 1회 실행**이다. 목적은 세 가지 —
(i) fp16에서 NaN이 나는지, (ii) 수율이 몇 %인지 실측, (iii) 24GB에서 `--max_seq_len`을
어디까지 올릴 수 있는지. 몇 시간이면 끝나고, 통과하면 바로 32B로 올라간다.

#### (c) 대신 **절단(truncation) 구현은 이월한다**

원래 4.4절 2번으로 잡았던 span offset 보존 절단은 며칠이 걸릴 수 있다. 24GB에서는
**`--max_seq_len` 상향만으로도** 필터에 걸리는 비율이 크게 준다. 여기에 **suite 층화
샘플링**(작은 수정)과 **suite별 카운트 기록**만 붙이면 "균등하게" 지시에 정직하게 답할 수
있다 — "완전 균등"이 아니라 "층화 + 잔여 불균형을 수치로 공개"로 보고한다.

## 1. 실행 환경 — SSH 공용 서버로 이전

### 1.1 서버 제약 (교수님 규칙)

> - 누가 돌리고 있을 수도 있으니 그럴 경우 기다리고 쓸 것
> - `~/jbwon` 에서만 작업할 것. 다른 곳 절대 수정 금지. 패키지 설치도 최대한 영향 없게

`~` 자체가 공용일 가능성이 높다는 뜻으로 해석한다. 파이썬 생태계가 기본으로 홈에
쏟아붓는 캐시가 전부 남의 환경 오염이 되므로 **전부 `~/jbwon` 안으로 접어야 한다.**

| 무엇 | 기본 위치 | 대응 |
|---|---|---|
| HF 모델 가중치 (수십 GB) | `~/.cache/huggingface` | `HF_HOME` |
| pip 캐시 | `~/.cache/pip` | `PIP_CACHE_DIR` |
| torch hub/extensions | `~/.cache/torch` | `TORCH_HOME`, `TORCH_EXTENSIONS_DIR` |
| matplotlib 설정 | `~/.config/matplotlib` | `MPLCONFIGDIR` |
| `pip install --user` | `~/.local/lib/python*` | **금지** (공용 파이썬 import 경로를 바꿈) |
| pyenv | `~/.pyenv` + `.bashrc` 수정 | **금지** (2절 참고) |

`~/jbwon/env.sh`를 만들어 매 세션 `source` 하는 방식:

```bash
# ~/jbwon/env.sh
export JB=~/jbwon
export XDG_CACHE_HOME=$JB/.cache          # ~/.cache/* 대부분 일괄 포섭
export HF_HOME=$JB/.cache/huggingface
export TORCH_HOME=$JB/.cache/torch
export PIP_CACHE_DIR=$JB/.cache/pip
export MPLCONFIGDIR=$JB/.cache/matplotlib
export TORCH_EXTENSIONS_DIR=$JB/.cache/torch_extensions
export TRITON_CACHE_DIR=$JB/.cache/triton
export CUDA_DEVICE_ORDER=PCI_BUS_ID       # nvidia-smi 번호와 일치
source $JB/miniforge3/bin/activate $JB/envs/atlas
```

추가 규칙: **`sudo` 금지**, **`git config --global` 금지**(저장소 로컬 설정만 사용).

### 1.2 Python 3.8.19는 쓸 수 없다 — Miniforge를 `~/jbwon`에

서버 기본 파이썬이 3.8.19인데 이건 하드 블로커다:

- `transformers==4.51.3` → Python ≥3.9 (4.47에서 3.8 지원 종료)
- `torch` ≥2.5 → Python ≥3.9
- **`agentdojo` → Python ≥3.10.** P4 트랙 전체가 이 패키지에 얹혀 있음

`run-guide.md` 0단계의 pyenv 방식은 **서버에서 쓰면 안 된다.** pyenv는 파이썬을 소스
빌드하므로 `libssl-dev`/`libffi-dev` 등 시스템 패키지를 요구하고, 없으면 root가 필요하다.

대신 Miniforge를 `~/jbwon` 안에 넣는다 — 단일 디렉토리 자기완결형, root 불필요,
빌드 의존성 불필요, `-b` 플래그로 `.bashrc`도 안 건드린다:

```bash
curl -L -O "https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-Linux-x86_64.sh"
bash Miniforge3-Linux-x86_64.sh -b -p ~/jbwon/miniforge3
# conda create가 아니라 venv — conda는 ~/.conda/environments.txt를 홈에 쓴다
~/jbwon/miniforge3/bin/python -m venv ~/jbwon/envs/atlas
```

디스크는 2.1T로 널널하므로 모델 캐시 용량 걱정은 없다. (**참고**: 4bit는 다운로드
용량을 줄여주지 않는다. bitsandbytes는 fp16 가중치를 전부 받은 뒤 로드 시점에
양자화하므로 32B는 디스크에 60GB대로 내려앉는다.)

### 1.3 GPU: Titan RTX 24GB × 3 — dtype은 **bf16 유지** (2026-08-21 실측으로 확정)

> ⚠️ **이 절의 초판 결론("Turing에는 bf16이 없으니 fp16으로 내려야 한다")은 틀렸다.**
> 서버 실측으로 정반대임이 확인됐다. 아래가 정정된 내용이다.

#### 실측 결과 (Titan RTX sm_75 · torch 2.13.0+cu126 · Qwen2.5-0.5B · 템플릿 3개)

| dtype | relevance NaN | fp32 대비 오차 | 소요 | 판정 |
|---|---|---|---|---|
| fp32 | 0 | — | 18.3s | 기준 |
| **bf16** | **0** | 2e-2 | **20.7s (+13%)** | ✅ **채택** |
| fp16 | **140/336 (템플릿 1/3)** | — | — | ❌ **사용 불가** |

#### (1) fp16은 못 쓴다 — Qwen2 activation outlier

Qwen2 계열은 특정 레이어의 activation이 fp16 최대값(65504)을 넘고, LRP 패치된 backward가
그 값을 타면 NaN이 된다. 근거 두 가지:

- NaN이 **layer 0~9에만** 나타난다. backward는 layer 27→0 순이므로, 중간에서 생긴 NaN이
  이전 레이어로 전파된 형태다.
- **타깃 로짓 scale을 0.01 / 1 / 100으로 바꿔도 NaN 개수가 140으로 동일하다.**
  loss scaling은 gradient 크기만 옮기므로, scale 불변이라는 건 **forward 쪽에서 이미
  터졌다**는 뜻이다. 즉 loss scaling으로는 살릴 수 없다.

판별 도구: `tools/diag_dtype.py` (overflow / underflow / 회복 불가를 구분한다).

#### (2) Turing의 bf16은 죽지도, 느리지도 않았다

bf16 하드웨어는 없지만 PyTorch가 에뮬레이션으로 돌리고, **오버헤드가 fp32 대비 13%**에
불과했다. `CUBLAS_STATUS_NOT_SUPPORTED`는 나지 않았다.
(0.5B 기준 측정이므로, 큰 모델에서 비율이 달라지는지는 S2에서 재확인한다.)

#### (3) 왜 bf16이 맞는가

우리 문제는 **정밀도가 아니라 동적 범위**였다. bf16은 지수 범위가 fp32와 같아 (1)의
overflow가 원천적으로 안 나고, 정밀도 손실은 정상 템플릿 기준 fp32 대비 2e-2로 충분하다.
메모리는 fp32의 절반이라 32B 4bit에서 결정적이다.

#### (4) 부수 효과 — 기존 결과와 직접 비교된다

Colab/5070Ti의 모든 기존 실험이 bf16이었다. 서버도 bf16이므로 **초판에서 경고했던
"dtype 다른 결과를 같은 비교표에 섞지 말 것" 문제가 사라진다.** 8/19 이전 결과와 이번
사이클 결과를 한 표에 놓을 수 있다.

#### 그래도 `--dtype`과 NaN 가드는 남긴다

`--dtype {auto,bf16,fp16,fp32}`은 그대로 두되 **`auto`는 CUDA에서 항상 bf16**을 고른다.
인자를 남기는 이유는 (a) 위 대조 실험을 재현할 수 있어야 하고, (b) 다른 모델 계열에서
같은 문제가 나면 fp32로 도피할 길이 필요하기 때문이다. 해결된 dtype은 `env.json`과
`summary.txt` 헤더, 그리고 **결과 폴더 이름**에까지 기록된다.

**NaN 가드는 fp16을 안 쓰더라도 반드시 필요하다.** 이번에 실제로 잡아낸 실패 모드가
"에러 없이 그럴듯한 숫자가 나오는" 것이었다 — `aggregate_scores`가 NaN을 평균에 섞으면
`topk_heads`가 점수 순서가 아니라 **인덱스 순서**((0,0),(0,1),…)를 반환해
`jaccard=0.000`, `control_heads_both=[]`로 찍힌다. `run_pipeline.py`/`compare_head_sources.py`
양쪽에 가드를 넣고, 제외 개수를 `n_templates_used` / `nan_excluded` / `n_nan_skipped`로
결과에 남긴다 (**OOM 스킵과 반드시 구분**).

### 1.4 GPU 점유 — 공용이므로 매번 확인

```bash
nvidia-smi --query-compute-apps=gpu_uuid,pid,used_memory --format=csv
nvidia-smi --query-gpu=index,memory.used,memory.total --format=csv
```

비어 있는 GPU만 `CUDA_VISIBLE_DEVICES`로 잡는다. **3장을 관성적으로 다 잡지 않는다** —
32B 4bit도 24GB 한 장에 들어가므로 1장만으로도 진행된다. 남의 프로세스는 당연히 kill 금지.
tmux 세션 이름에 식별자와 GPU 번호를 넣어 다른 사람이 오해하지 않게 한다
(`tmux new -s jbwon-gpu1`).

**3장이 비어 있을 때의 활용법**: 한 모델을 3장에 쪼개지 말고 **3개 실험을 동시에** 돌린다.
이유는 두 가지 — (i) 남은 작업(3소스 비교, heldout sweep, top-K sweep)이 전부 독립 실행이라
그냥 3배 빨라지고, (ii) `device_map="auto"`로 레이어를 쪼개면 attention hook과 edge ablation이
여러 device에 걸치는데 `compare_head_sources.py:153,164`의 OOM 처리·메모리 로깅이 device 0만
보기 때문에 현재 코드로는 오작동한다. 마침 `discover-parallel`이 배치마다 새 프로세스를
띄우는 구조라 3장에 그대로 매핑된다.

### 1.5 브랜치 전략 — **실험 전용 브랜치를 만들지 않는다**

검토 결과 분기가 이득 없이 비용만 늘린다:

- 코드가 이미 완전히 이식 가능하다 (하드코딩 경로 0, 환경 차이는 전부 CLI 인자).
  서버용으로 고쳐야 할 건 dtype 하나뿐이고 그건 인자로 흡수된다
- 저장소 2.2MB, `results/` 606KB — clone/push 왕복 부담이 없다
- **브랜치를 나누면 재현성이 나빠진다.** `results/`에 커밋되는 숫자와 그걸 만든 코드는
  같은 선형 히스토리 위에 있어야 추적이 된다

대신 역할만 나눈다:

```
로컬(5070Ti) = 분석 · 문서 · 발표자료 편집 + 소형 모델 스모크
서버(SSH)    = 실행 전용. 코드는 pull만, results/ 만 커밋해서 push
```

서버에서 코드를 편집하지 않는 규칙만 지키면 충돌은 거의 없다. `results/`는 실행마다
새 폴더라 구조적으로 충돌하지 않는다.

## 2. internal/external head 겹침 — 합성 한정 예비 결과 (후순위)

**교수님 지시 3번에 대한 예비 답. 기존 결과 파일만으로 산출했다 (GPU 불필요).**

> **이 절의 수치는 합성 데이터셋 기준이며 예비 결과다.** 정식 분석은 AgentDojo 재라벨링
> 이후로 미뤘다 — 이유와 설계는 [2.6절](#26-후순위로-미룬-이유와-정식-분석-설계-agentdojo-재라벨링).
> 다만 **이미 산출된 공짜 결과이므로 폐기하지 않고**, 발표에서 "합성 한정 예비"로 명시해
> 보고한다. 8/26 사이클에서 이 축에 추가 GPU 시간을 쓰지 않는다.

`head_ranking.py:83-108`의 `summarize_overlap`이 이미 `internal_heads`/`external_heads`를
따로 구해 반환하고 있었고, 7/31 P7 실행(`results/2026-07-31_Qwen-Qwen2-5-1-5B-Instruct/summary.txt`)에
top-K sweep이 남아 있어 겹침 정도를 전부 복원할 수 있었다.

### 2.1 Qwen2.5-1.5B — top-K별 겹침 (28층 × 12헤드 = 336 슬롯)

| K | 교집합 | internal-only | external-only | jaccard | 우연 기대값 | **우연 대비** | knockout (k=교집합) |
|---|---|---|---|---|---|---|---|
| 5 | 3 | 2 | 2 | 0.429 | 0.007 | **61배** | 0.9118 → 0.3464 (불완전) |
| 10 | **9** | **1** | **1** | **0.818** | 0.015 | **55배** | 0.9118 → **0.0000** |
| 20 | 14 | 6 | 6 | 0.538 | 0.031 | **17배** | 0.9118 → **0.0000** |
| 40 | 32 | 8 | 8 | 0.667 | 0.063 | **11배** | 0.9118 → **0.0000** |

(internal-only / external-only는 두 집합 크기가 모두 K이므로 `K − 교집합`으로 확정된다.
우연 기대값은 `head_ranking.expected_jaccard_by_chance` 산출값이며 K=20 값 0.031은
summary.txt에 직접 기록돼 있다.)

### 2.2 Qwen2.5-7B (4bit) — K=20 (28층 × 28헤드 = 784 슬롯)

| 모델 | jaccard(int,ext) | 교집합 | int-only | ext-only | 우연 기대값 | 우연 대비 |
|---|---|---|---|---|---|---|
| 1.5B | 0.538 | 14 | 6 | 6 | 0.031 | 17배 |
| **7B 4bit** | **0.600** | **15** | **5** | **5** | 0.013 † | **46배** |

† 7B 실행은 P7(우연 기준선 도입) 이전이라 파일에 값이 없다. 같은 공식으로 이 문서에서
계산: `E[교집합] = K²/N = 400/784 = 0.510`, `jaccard ≈ 0.510/(40−0.510) = 0.013`.

heldout 스타일별 변동(1.5B, K=20): **0.481 ~ 0.600** (교집합 13~15개). 공격 문구 스타일을
바꿔도 겹침 구조가 유지된다.

### 2.3 해석 — 발표에 쓸 수 있는 것

1. **internal head와 external head는 우연 대비 11~61배 겹친다.** 출력 형식(자유 텍스트 vs
   tool-call JSON)이 달라도 "명령을 명령으로 받아들이는" 회로는 대체로 공유된다.
2. **그러나 완전히 같지도 않다.** K=20에서 각 6개(1.5B) / 5개(7B)가 채널 전용이다.
   P3의 가설("채널 전용 head가 존재하는가")에 대한 답은 **존재한다, 단 소수다.**
3. **겹침이 K에 대해 비단조다 — 이게 핵심.** K=10에서 9/10(0.818)로 최대이고, K를 늘리면
   겹침 비율이 오히려 떨어진다. 즉 **최상위권일수록 채널 공유, 하위로 갈수록 채널 특화**.
   "공유 core + 채널별 주변부" 구조를 시사한다.
4. **그 공유 core가 방어 효과의 주역이다.** 9/10이 겹치는 K=10에서 knockout이 완전히 듣고
   (`malicious 0.0000`), 3/5만 겹치는 K=5에서는 안 듣는다(`0.3464`). 방어에 필요한 건
   공유 core 전체이지 채널 전용 head가 아니다.

### 2.4 남은 갭 — 전부 후순위로 이월

| 갭 | 비용 | 시점 | 비고 |
|---|---|---|---|
| internal-only / external-only **멤버십 미저장** | **매우 낮음** | 서버 구성 후, 여유 있을 때 | `summarize_overlap`이 이미 반환 중. `run_pipeline.py` 출력 2줄 추가 후 1.5B 재실행이면 끝 (로컬 5070Ti로 수 분). **합성 기준이라 결론용으로는 못 씀** |
| 7B/14B top-K sweep 미실행 | 낮음 | 후순위 | 합성 기준이라 우선순위 없음 |
| **채널 전용 head만 knockout하는 대칭 실험** | 중간 | **AgentDojo 재라벨링 이후** | P3의 3번 항목. 2.3의 해석 4번을 실증하려면 필수지만, 합성 데이터로 하면 교란이 곱해진다 |
| 7B 우연 기준선이 파일에 없음 | — | ✅ 해결 | 이 문서에서 계산해 채움 |

### 2.5 확인 필요 — `jaccard(read,internal)`이 모든 실행에서 동일

전 실행(1.5B 5개 heldout + unseen + baseline, 7B 3개)에서 `jaccard(read,internal)`이
예외 없이 **0.290**이다. 같은 실행들에서 `jaccard(internal,external)`은 0.481~0.600으로
움직이는데 이 값만 고정돼 있다.

유력한 설명: heldout style은 **공격 문구 스타일**을 바꾸는 것이라(`dataset.py`), read head
탐색(`read_clean`/`read_injected`)에는 영향이 적고 internal/external 타깃에만 영향을 준다.
즉 read head가 안정적인 건 자연스럽다. 다만 1.5B와 7B가 **같은 값**인 것은 우연으로 보이며,
2.4의 멤버십 저장 작업을 할 때 `read_heads` 목록도 같이 찍어 한 번 확인한다. (우선순위 낮음)

### 2.6 후순위로 미룬 이유와 정식 분석 설계 (AgentDojo 재라벨링)

**미루는 이유.** internal/external 축은 **합성 데이터셋에만 존재한다**(`dataset.py:75,98-101`).
그런데 합성 데이터셋은 AgentDojo 등 외부 벤치마크 대비 품질이 낮고, `review-2026-07-29.md`에서
**content-availability 교란**으로 억제 수치가 부풀려졌을 가능성이 이미 확인됐다. 이 데이터
위에서 "채널 전용 head가 존재한다/안 한다"까지 결론 내면 교란이 곱해진다. 2.1~2.3의 수치는
**방향성 참고용 예비 결과**로 남기고, 결론은 외부 벤치마크에서 낸다.

**정식 분석 설계 — AgentDojo에 채널 축 이식.** AgentDojo는 태생이 tool-calling이라
external(주입 명령이 tool_call 인자까지 침투) 대응물만 자연스럽다. internal(주입 명령이
assistant의 자유 텍스트 답변을 오염) 대응물을 만들려면 다음이 필요하다:

1. **프롬프트 변형** — `adapters/agentdojo.py`에 `build_agentdojo_internal_example`를 신설.
   기존 `build_agentdojo_example`에서 system의 tool 스펙(`_tool_list_text`)을 제거하고
   자유 텍스트 응답을 유도하는 prefix로 교체. `D_benign`/`D_inj` span 분리는 그대로 재사용.
2. **`exec_target` 재정의 — 여기가 "재라벨링"의 실체.** AgentDojo의 injection task는
   "특정 tool을 호출하게 만드는 것"으로 성공이 정의돼 있어서, tool이 없는 자유 텍스트
   모드에서는 그 정의가 성립하지 않는다. **injection task를 유형별로 분류해, 자유 텍스트로도
   성공 판정이 가능한 것(정보 유출·특정 문구 출력 계열)만 골라내는 작업**이 선행돼야 한다.
   유형 분류 없이 tool 이름 첫 토큰을 그대로 쓰면 P2-c의 InjecAgent 매핑과 같은 proxy가 되어,
   `review-2026-07-29.md`가 지적한 "독립 정보 없는 지표" 문제를 반복한다.
3. **대칭 knockout 검증** — `external_only`만 죽였을 때 tool-call 쪽만 떨어지고 자유 텍스트
   오염은 유지되는지(반대 방향도) 확인. 이게 2.3의 해석 4번에 대한 실증이다.

**비용 판단**: 2번이 실질적으로 새로운 라벨링 작업이라, 이번 4개 항목 중 **숨은 비용이 가장
크다.** 8/26 사이클에서는 착수하지 않고, 항목 1·2·4(suite 균등화 / 스케일업 / split 재설계)가
정리된 뒤 다음 사이클로 넘긴다.

### 2.7 발표에서 명시할 것

- 2.1~2.3 수치는 **합성 한정 예비 결과**임을 표 제목에 명시한다
- "AgentDojo에는 이 축이 없다"는 점과, 정식 분석을 위해 **injection task 재라벨링이
  선행돼야 한다**는 점을 함께 보고한다 (미룬 게 아니라 **선행 조건이 있다**는 서술)

## 3. 모델 스케일업 설계

### 3.1 제약 — 병목은 lxt가 아니라 우리 코드의 2-패밀리 분기

**2026-08-21 조사 결과 (lxt 2.1 소스 직접 확인).** `lxt/efficient/models/__init__.py`의
`DEFAULT_MAP`은 **llama / qwen2 / qwen3 / gemma3 / bert / gpt2 / vit**를 지원한다.
`monkey_patch(module)`은 이 맵에서 자동으로 patch를 찾으므로, **lxt 쪽에 할 일은 없다.**
막고 있는 건 `attn_relevance.py:37-43`이 `qwen2`/`llama`만 분기한다는 점뿐이다.

**다만 lxt README의 지원 상태 표에 중요한 단서가 있다:**

| lxt 지원 표 | 상태 |
|---|---|
| LLaMA 2/3 | ✅ |
| **Gemma 3** | ✅ (lxt의 대표 예시로 쓰일 만큼 검증됨) |
| Qwen 2 | ✅ |
| **Qwen 3** | 🧪 **"Attribution skewed toward first token"** |

| 후보 | 코드 수정 | 24GB 1장 | 비고 |
|---|---|---|---|
| **Qwen2.5-32B 4bit** | **없음** | ~18GB, 들어감 | family 그대로. lxt qwen2 ✅ |
| **Llama-3.1-8B fp16** | **없음** | ~16GB, 들어감 | `--family llama` 이미 있음. HF 라이선스 동의 필요 |
| Qwen3-8B | 분기 1개 (~6줄) | 여유 | ⚠️ **lxt가 first-token skew를 경고**. 아래 3.1.1 |
| Gemma-3-27B 4bit | 분기 1개 (~6줄) | ~16GB | lxt는 ✅지만 다른 제약 3개. 아래 3.1.2 |

> ℹ️ lxt 2.1은 `transformers==4.52.4`로 테스트됐다고 README에 적혀 있다. 우리 핀은 4.51.3.
> qwen2/llama에서는 이 조합이 이미 실측으로 돌아갔지만(7/27~8/19 전 실행), qwen3/gemma3
> 경로는 이 조합에서 검증된 적이 없다. 붙일 때 첫 실행에서 확인할 것.

#### 3.1.1 Qwen3-8B — 배선은 싸지만 결과 신뢰도가 문제

lxt가 **"attribution이 첫 토큰으로 쏠린다"**고 명시적으로 경고한다. 우리 방법론은
relevance를 **D_inj key-token span에 걸쳐 합산**하는 것(`ρ^h_j = Σ_i ReLU(rel)[i,j]`,
`score(J) = Σ_{j∈J} ρ^h_j`)이라, relevance 질량이 position 0에 흡수되면 D_inj 점수가
계통적으로 눌린다. head **순위**까지 무너지는지는 별개 문제지만, **알려진 병리 위에
결론을 쌓는 셈**이다.

쓰려면 배선보다 **진단이 먼저**다 — 같은 프롬프트에서 position별 relevance 분포를 찍어
position 0이 지배하는지 확인하고, 지배한다면 첫 토큰을 제외한 정규화가 필요한지 판단한다.
이 진단 비용을 감안하면 **세대 축은 이번 사이클 우선순위가 아니다.**

#### 3.1.2 Gemma-3-27B — lxt는 되지만 다른 제약 3개

정정: 이전 판의 "lxt 미지원"은 **틀렸다.** `lxt/efficient/models/gemma3.py`가 있고
`DEFAULT_MAP`에 등록돼 있다. 그래도 아래 때문에 이번 사이클에는 권하지 않는다:

1. **멀티모달 래퍼** — Gemma 3는 4B 이상이 이미지 입력을 받는 `Gemma3ForConditionalGeneration`
   이다. 텍스트 타워만 쓰려면 로드 경로를 따로 잡아야 한다(`Gemma3ForCausalLM`).
2. **sliding-window local attention** — Gemma 3는 대부분의 레이어가 전역이 아닌 로컬
   윈도우 attention이다. **AgentDojo의 긴 tool 응답에서는 D_inj span이 윈도우 밖으로
   나갈 수 있고**, 그러면 그 레이어의 head는 구조적으로 D_inj를 볼 수 없어 relevance가
   0이 된다. 4절의 길이 문제와 정면으로 얽힌다.
3. **게이트 모델** — HF 라이선스 동의 + 토큰 필요.

여기에 3.2의 교란(스케일·패밀리·세대 동시 변경)이 그대로 남는다.

### 3.2 축을 분리할 것 — 27B는 세 변수를 동시에 바꾼다

27B(Gemma)로 가면 **스케일 · 패밀리 · 세대**가 한꺼번에 바뀐다. head가 전이되지 않는
결과가 나와도 셋 중 무엇 때문인지 가릴 수 없다. 축을 하나씩 분리한다:

- **스케일 축** (family 고정): Qwen2.5-7B → **32B 4bit**. 코드 수정 0
- **패밀리 축** (스케일 고정): Qwen2.5-7B → **Llama-3.1-8B**. 코드 수정 0

이 조합이면 서버 도착 첫날부터 코드 수정 없이 두 축을 다 돌릴 수 있다.

**세대 축(Qwen3-8B)은 이번 사이클에서 빼는 것을 권한다.** 3.1.1대로 배선 자체는 6줄이지만,
lxt가 first-token skew를 경고하고 있어 진단이 선행돼야 한다. 스케일·패밀리 두 축의 결과를
먼저 확보하는 편이 발표 서사에도 낫다.

### 3.3 스케일업의 숨은 비용 — 4절과 곱해진다

eager attention backward의 지배 텐서는 `H × T²`다. 32B(64층 · 64헤드)를 T=2000으로 돌리면
**층당 512MB**, T=4000이면 **2GB**다. **모델 키우기와 길이 필터 풀기를 동시에 하면 24GB에서도
7B/16GB보다 나빠진다.**

**이것이 [6절](#6-실행-순서)에서 S2(7B 스모크)를 게이트로 둔 이유다.** `max_seq_len`을
어디까지 올릴 수 있는지는 7B에서 실측한 뒤, **32B에서는 그 값을 그대로 쓰지 말고
헤드 수 비율만큼 낮춰 잡는다** (7B 28헤드 → 32B 64헤드, 약 2.3배).

## 4. AgentDojo suite 균등화 — VRAM 문제가 아니다

교수님 지시 1번은 "travel이 OOM으로 빠졌으니 균등하게"인데, 코드를 보면 원인이 세 겹이고
**VRAM 증설로는 해결되지 않는다.**

### 4.1 원인 (1) — 길이 필터 자체가 suite 편향이다

`compare_head_sources.py:118-128`의 `--max_seq_len 2000` 필터가 "상위 롱테일 ~6%"를 자르는데,
긴 tool 응답은 **travel/workspace에 몰려 있다**(주석에 "특히 workspace suite, 최대 ~9600 토큰"으로
명시). 즉 필터가 곧 계통적 배제다. VRAM을 늘려도 필터를 그대로 두면 균등해지지 않는다.

### 4.2 원인 (2) — `compute_head_relevance`의 프로세스 전역 메모리 누수

`compare_head_sources.py:8`과 todo.md P2-d에 기록된 버그. 호출당 ~0.12GB씩 누적된다.
파일에 남은 실측: **길이 필터를 걸고도 150번 중 18번만 성공**, head_n=60에서 44개 OOM.
예시 크기 문제가 아니라 누적 문제라 **24GB는 터지는 시점을 늦출 뿐이다.**

### 4.3 원인 (3) — 스킵이 suite별로 기록되지 않는다

`n_skipped_oom`(`compare_head_sources.py:143-179`)은 **총합만** 남는다. 어느 suite가 몇 개
빠졌는지 사후 확인이 불가능하다. 균등했다고 주장하려면 이 카운트가 suite별로 결과 JSON에
있어야 한다.

### 4.4 할 일

**이번 사이클(S3)에서 하는 것 — "최소 균등화"**:

1. **`--max_seq_len` 상향.** 24GB이므로 2000 → 3000~4000이 되는지 **S2에서 7B로 실측**한다.
   필터에 걸리는 비율이 줄면 그만큼 travel/workspace의 계통적 배제가 완화된다.
   **코드 수정 없음 — 파라미터만.**
2. **suite별 층화 샘플링.** 현재 `split_pairs`는 suite와 무관한 무작위라 균등을 보장하지
   않는다. suite별 동일 쿼터로 뽑는다. **작은 수정.**
3. **suite별 성공/스킵/NaN 카운트를 결과 JSON에 기록.** OOM 스킵과 fp16 NaN 스킵을 구분한다
   (NaN 분리는 이미 구현됨 — 1.6절). **suite별로 쪼개는 것만 남았다.**
4. **`discover-parallel`을 기본 경로로.** 배치마다 새 프로세스=새 CUDA 컨텍스트라 누수를
   배치 경계에서 리셋한다. GPU 3장에 그대로 매핑된다. **파라미터 선택.**

> **이 조합으로 주장할 수 있는 것**: "완전 균등"이 아니라 **"suite 층화로 뽑았고, 잔여
> 불균형은 suite별 카운트로 공개한다"**. 1·3번이 있으면 어느 suite가 얼마나 빠졌는지
> 사후 검증이 가능해지므로, 8/19처럼 "travel이 통째로 빠진 걸 나중에 발견"하는 일은 없다.

**이월 (6절 이월 A)**:

5. ~~**필터 대신 절단(truncation)**~~ — 예시를 버리지 말고 tool 응답 본문을 잘라 길이를
   맞추는 정공법. 단 `D_benign`/`D_inj` **span offset을 보존하며 재계산**해야 해서 며칠이
   걸릴 수 있다. **1번(`max_seq_len` 상향)으로 불충분하다고 S3에서 판명될 때** 착수한다.

## 5. AgentDojo head 탐색과 split — 지금 split엔 누수가 있다

`adapters/agentdojo.py:263-270`이 (user_task × injection_task) **전조합**을 만들고,
`split_pairs`가 이걸 무작위로 나눈다. 그러면 **같은 user_task가 탐색셋과 평가셋 양쪽에
들어간다.** "새 데이터에서도 통하는가"를 보려는 split의 취지가 무너진다.

- **user_task 단위 group split** — suite 층화를 유지하면서 한 user_task가 한쪽에만 가도록.
  **이번 사이클 S4에 포함.** 교수님 지시 4번("데이터셋 split 해서 하기")에 답하는 것이
  이것이고, 누수를 안 고치면 split을 했다는 주장 자체가 성립하지 않는다.
- **leave-one-suite-out** — banking/slack/travel로 찾고 workspace로 평가.
  P2-a의 held-out style과 논리가 같아 발표에서 설득력이 훨씬 크다.
  **6절 이월 B** — S5까지 끝내고 시간이 남으면 끼워 넣는다. group split만으로도
  지시 4번은 충족되므로 필수는 아니다.

## 6. 실행 순서

[0.1절](#01-이번-사이클의-줄기--모델-2개로-같은-실험을-반복한다)의 줄기를 단계로 편 것.
**S2(7B 스모크)가 게이트**다 — 여기 수치를 보고 S3의 파라미터를 정한다.

| 단계 | 내용 | GPU | 산출물 |
|---|---|---|---|
| **S0** | internal/external 겹침 — 기존 결과에서 복원 (합성 한정 예비) | — | ✅ **완료** (2절) |
| **S1** | 서버 셋업 — Miniforge 3.11, `env.sh`, `requirements.txt` 확정 핀, `external_injecagent` clone | 0장 | 동작하는 환경 + 첫 `env.json` |
| **S2** | **7B 스모크** — 기존 코드로 AgentDojo `discover-parallel` 1회 | 1장 | **fp16 NaN 유무 · 수율(%) · `max_seq_len` 상한** |
| **S3** | 최소 균등화 — `max_seq_len` 상향 + **suite 층화 샘플링** + **suite별 카운트 기록** | 1장 | suite별 표본 수가 찍힌 결과 JSON |
| **S4** | **Qwen2.5-32B 4bit** — AgentDojo 헤드 탐색 (+ **user_task group split**) | 1~3장 | 32B 헤드 집합 + split 정보 |
| **S5** | **검증** — S4의 헤드로 평가셋에 `run_agentdojo_eval` 네이티브 채점 | 1장 | 32B knockout 결과 |
| **S6** | **Llama-3.1-8B로 S4~S5 반복** | 1~3장 | 패밀리 축 대조 결과 |

**단계별 게이트 조건** — 다음으로 넘어가기 전에 확인할 것:

| 게이트 | 통과 조건 | 실패 시 |
|---|---|---|
| S2 → S3 | `n_nan_skipped`가 0에 가까움 | fp32로 올려 재현되는지 확인 (1.3절) |
| S2 → S4 | 수율이 쓸 만함 (현재 기준선 18/150) | `--batch_size` 축소, `head_n` 상향으로 절대 표본 확보 |
| S3 → S4 | suite 4개 모두 표본이 0이 아님 | 표본 0인 suite를 결과에 명시하고 그 한계로 보고 |
| S4 → S5 | 헤드 집합이 layer 0에만 몰리지 않음 | 기존 7B 결과와 layer 분포 비교 (교란 신호) |

**왜 이 순서인가**: S2를 건너뛰고 S4로 직행하면, OOM이나 빈 결과가 나왔을 때 원인이
**메모리 누수인지 · 32B 크기인지 · fp16 NaN인지 · 층화 로직 버그인지** 가릴 수 없다.
S2는 코드 작업이 아니라 기존 코드 1회 실행이므로 비용 대비 방어력이 크다.

**8/26 사이클 범위는 S6까지.** 아래는 다음 사이클로 이월 —
GPU 여유가 생겨도 S1~S6이 끝나기 전에는 착수하지 않는다:

| 이월 | 내용 | 선행 조건 |
|---|---|---|
| A | **span offset 보존 절단(truncation)** — 길이 필터를 완전히 없애는 정공법 (4.4절 2번) | S3의 `max_seq_len` 상향으로 부족하다고 판명될 때 |
