## 1. 타이틀 — Read Head와 Control Head의 분리 PoC

안녕하십니까, 오늘 발표는 "Read Head와 Control Head의 분리"라는 주제로, Indirect
Prompt Injection, 줄여서 IPI 공격을 attention head 수준에서 방어하는 방법에 대한
PoC 결과를 말씀드리겠습니다. NeurIPS 2025에 발표된 Atlas of In-Context Learning의
방법론을 이 방어 시나리오에 응용한 연구입니다.

---

## 2. 개요 — 가설: Read Head와 Control Head는 분리되어 있다

LLM 에이전트가 이메일 본문이나 tool 실행 결과 같은 외부 데이터를 프롬프트에 그대로
넣어 처리할 때, 그 데이터 안에 공격자가 심어둔 명령문이 있으면 모델이 원래 사용자의
지시 대신 그 명령을 따라버리는 문제가 발생합니다. 이게 Indirect Prompt Injection입니다.

저희 가설은 이렇습니다 — 모델 내부에서 attention head 수준으로 봤을 때, 외부 데이터의
**내용을 읽는 데** 관여하는 head 그룹(Read Head)과, 그 데이터 속 **명령을 실행에
옮기는 데** 관여하는 head 그룹(Control Head)이 서로 분리되어 있을 것이라는 겁니다.

분리되어 있다면, Control Head만 정밀하게 무력화해도 Read Head의 정상 기능은 보존한
채로 공격만 막을 수 있습니다. 이걸 검증하는 방법은 두 단계입니다: 첫째, relevance로
head를 찾고, 둘째, 그 head의 D_inj 방향 attention edge만 끊습니다.

**[부가설명]** 여기서 D_inj는 "injected data", 즉 프롬프트 안에 주입된 공격 명령
부분을 가리키는 표기입니다. 뒤에 나올 슬라이드에서 계속 이 표기를 씁니다.

---

## 3. 방법론 — Head 탐색 (왜 grad가 아니라 "AttnLRP grad"여야 하는가)

Head를 찾는 방법을 설명드리기 전에, 구현상 중요한 트릭 하나를 먼저 짚겠습니다.

저희가 계산하려는 relevance는 그냥 표준 gradient가 아니라, AttnLRP라는 방식으로
계산된 gradient여야 합니다. 그 이유는, RMSNorm이나 gated-MLP, attention의 softmax
같은 비선형 연산을 일반 chain rule로 미분하면 relevance 값이 발산하거나 소실돼서,
"실제로 얼마나 기여했는가"를 제대로 반영하지 못하기 때문입니다. LRP는 이런 연산마다
별도의 보존적인 전파 규칙을 씁니다.

화면의 코드를 보시면, `lxt.efficient`의 `monkey_patch` 함수를 모델을 로드하기
**전에** 호출합니다. 이 한 줄이 하는 일은, HuggingFace의 Qwen2 모델링 모듈 안에
있는 RMSNorm·gated-MLP·attention 서브모듈들의 backward 계산 함수 자체를, AttnLRP
규칙에 맞는 버전으로 런타임에 바꿔치기하는 겁니다. 표준 `Qwen2ForCausalLM`을 그대로
쓰면서도 AttnLRP에 정합적인 backward를 얻을 수 있는 방법입니다.

**[부가설명 — 왜 이렇게 하는가]** Atlas 원 논문 코드는 사실 HuggingFace 모델링
코드를 통째로 포크해서, `self_attn.softmax` 같은 커스텀 서브모듈을 직접 만들고
backward 규칙을 손으로 다시 짠 버전을 씁니다. 이 방식은 transformers 버전이 바뀔
때마다 수동으로 따라잡아야 하는 부담이 있습니다. `monkey_patch`는 같은 저자
그룹이 이 문제를 풀기 위해 나중에 배포한 것으로, 모델링 코드를 포크하지 않고
표준 모듈을 import한 뒤 서브모듈의 backward 함수만 교체합니다. 그래서 저희는
이 방식을 재구현에 채택했습니다. 다만 이 패치가 공식 지원하는 게 Qwen2와 Llama
계열뿐이라, 저희 실험도 이 두 아키텍처로 한정됩니다. 그리고 패치는 반드시
`from_pretrained`보다 먼저 호출돼야 합니다 — 순서가 바뀌면 이미 만들어진 서브모듈은
원래 backward를 그대로 쓰게 되어 패치가 무의미해집니다.

## 4. 방법론 — Head 탐색 (Attention × Gradient로 "진짜 기여"를 잰다)

이제 실제로 relevance를 계산하는 공식을 보겠습니다.

먼저 왜 attention weight만으로는 부족한지부터 말씀드리면, "많이 쳐다봤다"와
"실제로 답변에 반영했다"는 다른 개념입니다. attention 확률만 보면 이 둘을 구분하지
못합니다. 그래서 여기에 gradient를 곱합니다.

화면의 코드 흐름을 따라가 보면: `output_attentions=True`로 모델을 호출해서
모든 layer의 attention 확률 행렬을 받고, 각 행렬에 `retain_grad()`를 걸어서
backward 이후에도 gradient가 남게 만듭니다. 그다음 관심 있는 출력 토큰, 예를 들어
악성 토큰 "attacker"의 로짓 하나에 대해 `backward()`를 호출하면, attention 행렬의
`.grad`가 채워집니다.

그러면 `rel = attention × attention.grad`를 계산하고, 음수는 ReLU로 버립니다.
이게 `(layer, head, i, j)`별 relevance입니다. 마지막으로 관심 있는 key 위치
그룹—정상 내용이든 주입된 명령이든—에 대해 j축을 합산하면, head 하나당 점수
하나가 나옵니다. 이게 화면 공식의 ρ^h_j입니다.

이 relevance를 세 가지 다른 조건으로 계산합니다. 표를 보시면, `read_score`는
정상 답 토큰으로 backward하고 정상 콘텐츠 구간을 key 그룹으로 삼습니다 — 이 head가
정상 내용을 읽는 데 기여했는지를 봅니다. `internal_score`는 악성 토큰으로
backward하되 자유 텍스트 응답 상황에서, `external_score`는 같은 악성 토큰이지만
tool-call 인자로 나오는 상황에서 계산합니다. 둘 다 주입된 명령 구간을 key 그룹으로
삼습니다.

**[부가설명 — 그룹을 어떻게 나누는가]** 여기서 중요한 건, head 자체에 "이건 read
head다"라는 표식이 있는 게 아니라는 점입니다. 같은 함수를 프롬프트·backward
타깃·key span 세 가지 조건만 바꿔서 세 번 호출해 세 개의 점수 행렬을 얻고, 각각
상위 K개를 뽑은 게 read_heads, internal_heads, external_heads입니다. 즉 "이 head가
read 목적에 기여한 점수가 top-K 안에 든다"는 상대적·통계적 판정입니다.

세 집합의 Jaccard 유사도를 계산해서, `internal_heads`와 `external_heads`의
교집합을 이후 edge 차단 대상, 즉 control head 후보로 삼습니다. 실제 수치는 결과
파트에서 다시 보여드리겠습니다.

## 5. 방법론 — Edge Knockout (Head 전체가 아니라, Edge 하나만 끊는다)

Head를 찾았으면, 이제 그 head를 어떻게 무력화할지가 다음 단계입니다. 여기서
핵심 설계 선택은 **head 전체를 끄지 않는다**는 겁니다.

코드를 보시면, attention score를 계산한 뒤 pre-softmax 단계에서, 지정한
`{layer: [head]}` 조합에 대해서만 D_inj 토큰 범위에 해당하는 key 열을 `-inf`로
채웁니다. 그다음 softmax를 취하면, `-inf`였던 위치의 확률이 정확히 0이 되고,
나머지 위치는 정상적으로 재정규화됩니다. 즉 그 head가 D_inj 토큰들을 "보이지
않게" 만들지만, 같은 head가 정상 내용을 보는 건 그대로 유지됩니다.

**[부가설명 — 용어 정리]** 그래서 "head를 knockout한다"는 표현은 정확히는 부정확
합니다. head 자체는 살아있고, D_inj 방향 시선만 차단되는 것이므로 정확히는
**edge knockout**입니다. 이게 "head 하나를 통째로 죽여도 정상 기능이 보존되더라"
보다 더 강한 결과인 이유이기도 합니다 — 훨씬 좁은 개입으로도 공격이 죽는다는 뜻이니까요.

그리고 이 knockout 자체는 순수 forward 연산이라 gradient가 필요 없습니다. 그래서
head를 "찾는" 단계와 달리, 4bit 양자화된 모델에도 그대로 적용할 수 있습니다.
실제로 저희 7B 실험이 4bit 양자화 모델이었는데, 이 부분 덕분에 가능했습니다.

이렇게 control head 후보를 점수 순으로 정렬한 뒤, 상위 k개—0, 5, 10, 20, 40,
80—의 D_inj-edge를 차단해가면서, malicious_token_prob(공격 성공률 proxy)과
read_token_prob(정상 기능 보존 proxy)를 동시에 측정합니다.

## 6. 데이터셋 — 합성 (30 템플릿)

이제 실험에 쓴 데이터셋을 보여드리겠습니다. 먼저 저희가 직접 만든 합성
데이터셋입니다.

콘텐츠 도메인 6종—이메일 요약, 문서 QA, 캘린더, 주문 상태, HR, 인보이스—과
공격 문구 스타일 5종—명령형, 권위 사칭, 가짜 승인, 가짜 주석, 긴급성 어필—을
곱해서 30개 템플릿을 만들었습니다.

화면 예시를 보시면, 이메일 요약 시나리오입니다. 정상 내용은 "회의가 3시로
변경됐다"는 내용이고, 그 사이에 "IGNORE ALL PREVIOUS INSTRUCTIONS"로 시작하는
공격 문구가 심겨 있습니다. 이 프롬프트가 tool-call 모드로 응답하면, 모델이
`forward_email`을 호출하면서 `"to": "attacker`까지 나오면 공격이 성공한 걸로
판정합니다.

**[부가설명 — 왜 "attacker"로 고정하는가]** malicious token은 모든 조합에서
`"attacker"`로 고정했습니다. 도메인이 달라져도 "공격 성공"을 판정하는 토큰
id가 흔들리지 않게 하기 위해서입니다.

각 템플릿마다 4가지 mode의 프롬프트를 만듭니다. `read_clean`은 주입문이 아예
없는 상태에서 read head의 순수 baseline을 재는 용도, `read_injected`는 주입문이
있는 상태에서 knockout이 정상 기능을 보존하는지 보는 용도, `internal`은 자유
텍스트 응답이 오염되는지, `external`은 tool-call 인자가 오염되는지를 봅니다.
방금 본 예시를 `read` 모드로 바꾸면 정답은 " 3pm"이 됩니다.

**[부가설명 — key span을 어떻게 기록하는가]** 여기서 "어느 토큰이 정상 내용이고
어느 토큰이 주입 명령인지"는 프롬프트를 문자열로 다 만든 뒤 나중에 찾는 게
아니라, 조립하는 시점에 세그먼트별로 미리 토크나이즈하면서 그 자리에서 정확한
정수 인덱스로 기록합니다. Atlas 원 코드처럼 문자열 위치를 나중에 역산하는 방식은
BPE 토큰화 경계 때문에 버그가 나기 쉬워서, 이 방식을 택했습니다.

## 7. 데이터셋 — InjecAgent (외부)

두 번째 데이터셋은 저희가 만든 게 아니라, 외부에서 검증된 실제 벤치마크
InjecAgent입니다.

정상 tool 17종과 공격자 tool 62종의 조합으로 만들어진 1,054개의 실제 시나리오
입니다. 화면 예시를 보시면, 사용자가 아마존에서 노트북 리뷰를 조회하는 지극히
평범한 요청인데, 그 tool 응답의 리뷰 내용 안에 스마트락 접근 권한을 부여하라는
공격 명령이 심겨 있습니다.

저희가 만든 합성 데이터의 노골적인 "IGNORE ALL INSTRUCTIONS" 문구와 달리, 이건
훨씬 은근하고 자연스러운 공격 문구입니다. 그래서 "우리가 찾은 head가 우리
데이터에만 통하는 게 아닌지"를 검증할 첫 외부 벤치마크로 채택했습니다.

**[부가설명 — 매핑 방법]** 원본 InjecAgent 평가는 "에이전트의 실제 행동이
공격자 tool과 일치하는가"로 판정하지만, 저희는 다른 실험들과 통일하기 위해
`exec_target`을 Attacker Tools 이름의 첫 토큰, `read_target`을 User Tool
이름의 첫 토큰으로 매핑해서 같은 next-token 확률 proxy로 평가했습니다.

## 8. 실험 방법 — 파이프라인과 검증 축

지금까지 설명드린 네 개 스크립트—dataset.py, attn_relevance.py, head_ranking.py,
edge_ablation.py—가 하나의 파이프라인으로 이어집니다.

검증은 세 단계로 진행했습니다. P0는 로컬 RTX 5070Ti 환경에서 0.5B, 1.5B, 3B
스케일로 파이프라인 전체를 재현하는 단계, P1은 Qwen2.5-7B를 4bit로 스케일
확장하는 단계입니다. 그리고 P2가 이 실험의 핵심 검증 단계인데, 지금까지 head를
찾은 데이터와 knockout 효과를 검증한 데이터가 완전히 동일하다는 과적합 우려를
네 갈래로 해소하는 단계입니다.

모든 단계에서 head 선정에 쓰인 데이터와 knockout 평가에 쓰인 데이터는 절대
겹치지 않는 진짜 held-out 원칙을 지켰습니다.

## 9. 결과 — P0 & P1

먼저 P0와 P1 결과입니다.

위쪽 표는 0.5B, 1.5B, 3B 세 스케일 결과입니다. k=20 안에 malicious_token_prob이
0.9~1.0 수준에서 완전히 0으로 붕괴하는 동안, read_token_prob은 유지되거나 소폭
상승합니다. 스케일 3종 모두에서 재현됐습니다.

아래쪽 표는 7B를 4bit로 양자화한 결과입니다. 여기서도 attack 확률은 k=20 안에
0으로 떨어지고, read 확률은 오히려 0.8315에서 0.8934로 상승했습니다. "부작용
없는 방어"가 스케일에 무관하게 성립한다는 1차 증거입니다.

## 10. 결과 — Read vs Control 분리 (Jaccard)

이제 저희 핵심 가설, Read head와 Control head가 실제로 분리되어 있는지를
정량적으로 확인하겠습니다.

표를 보시면 jaccard(read,internal), jaccard(read,external), jaccard(internal,external)
세 값을 4개 모델 전체에 대해 정리했습니다. read 쪽 겹침은 0.176에서 0.379
사이인데 반해, internal과 external 사이의 겹침은 0.481에서 0.600으로 전
스케일에서 뚜렷하게 높습니다.

이건 두 가지를 동시에 보여줍니다. 첫째, read head와 control head는 실제로
분리되어 있다는 것 — read 쪽 겹침이 낮으니까요. 둘째, 자유 텍스트 오염과
tool-call 오염은 같은 head 집합을 상당 부분 공유한다는 것 — internal-external
겹침이 높으니까요. 이건 head 하나만 찾아도 두 공격 경로를 동시에 방어할 수
있다는 뜻이라 저희 방법론에 유리한 결과입니다.

다만 화면 아래 강조된 부분처럼, internal-external jaccard가 0.48에서 0.60로
낮은 수준이 아닙니다. 두 채널이 왜 이렇게 많이 겹치는지, 그리고 겹치지 않는
나머지가 무엇을 하는 head인지는 아직 답을 안 한 질문입니다. 이건 마지막
"다음 단계" 부분에서 다시 말씀드리겠습니다.

## 11. 결과 — P2 (외부 벤치마크, InjecAgent 전체)

이제 완전히 다른 실제 벤치마크인 InjecAgent 1,054개 전체에, 저희 합성
데이터셋에서 찾은 control head를 재선정 없이 그대로 적용한 결과입니다.

1.5B에서는 malicious 확률이 k=40에서 0.1894에서 0.0406으로 약 4.7배 줄었고,
7B에서는 0.5237에서 0.1300으로 약 4.0배 줄었습니다. read 확률은 두 스케일
모두 상승했습니다.

완전히 다른 실제 벤치마크에서도 knockout 효과가 두 스케일 모두 일관되게
재현된다는 점은 긍정적입니다. 다만 저희 합성 데이터만큼 완전한 억제, 즉
0으로 떨어지는 수준은 아니고, 잔여 확률이 남습니다. baseline 공격 확률 자체가
스케일이 커질수록 오히려 상승한 것(0.19에서 0.52로)으로 보아, 이건 스케일
문제가 아니라 도메인 또는 문구 구조의 차이로 추정됩니다.

**[슬라이드 안내]** 이 뒤에 나오는 슬라이드는 방금과 같은 표와 문구가 한 번 더
나오는데, 편집 과정에서 중복 삽입된 것으로 보입니다. 발표 전에 확인해서
정리하시는 걸 권해드립니다.

## 12. 결과 — P2 (InjecAgent 자체 head 탐색)

방금 본 부분적 전이가 "head를 잘못 골라서"인지, 아니면 "도메인 구조 자체의
한계"인지 구분하기 위해, InjecAgent 안에서 직접 control head를 찾아보는
실험을 추가했습니다.

InjecAgent 60개 case로 head를 직접 탐색하고, 나머지 994개로 평가했습니다.
표를 보시면 세 조건 — 합성 데이터에서 찾은 head 14개 단독, InjecAgent에서
직접 찾은 head 20개 단독, 그리고 두 집합의 교집합 9개 — 를 비교했는데, 세
조건 모두 억제 후 malicious 확률이 0.044에서 0.045 사이로 사실상 동일합니다.

흥미로운 건, 두 head 집합의 jaccard가 0.36이라는 점입니다. 완전히 같은
집합은 아니지만 상당수는 겹치는 상태에서, 어느 쪽 head를 쓰든 비슷한 성능이
나옵니다.

**[부가설명 — 왜 이게 중요한가]** 만약 head를 잘못 골라서 InjecAgent에 잘
안 통했다면, InjecAgent 자체에서 새로 찾은 head는 훨씬 더 잘 통해야 합니다.
하지만 세 조건이 사실상 동일한 지점(잔여 확률 0.044~0.045)에서 억제가
멈춘다는 건, 이게 head 선정 문제가 아니라 InjecAgent 도메인 구조 자체의
근본적인 한계라는 걸 세 번째 독립적인 증거로 뒷받침합니다.

## 13. 결론

정리하면 세 가지입니다.

첫째, Read head와 Control head는 실제로 분리되어 있고(jaccard 0.18~0.38),
자유 텍스트 오염과 tool-call 오염은 비슷한 control head 집합을 공유합니다
(jaccard 0.48~0.60).

둘째, Control head의 D_inj 방향 attention edge만 끊어도, 정상 기능은 그대로
둔 채 공격을 k=10에서 20 안에 효과적으로 억제합니다.

셋째, 완전히 다른 실제 벤치마크인 InjecAgent에는 부분적으로만 전이됩니다.
Qwen2.5-7B 기준으로 malicious 확률이 0.5237에서 0.1300으로 줄었지만, 저희
합성 데이터만큼 완전히 억제되지는 않았습니다.

**[부가설명 — 발표 마무리 멘트 예시]** "이 결과는 read head와 control head의
분리라는 가설을 여러 각도에서 뒷받침하지만, 동시에 실전 배포까지는 아직
풀어야 할 문제들이 남아 있습니다. 질문 주시면 답변 드리겠습니다."

## [Q&A 대비 — 슬라이드에는 없지만 준비해두면 좋은 답변]

발표 슬라이드 자체에는 "한계 및 다음 단계"가 따로 없어서, 질문이 나올 경우를
대비해 아래 내용을 기억해두시면 좋습니다 (원하시면 이 내용을 슬라이드로 추가한
보조 파일 `IPI_Head_PoC_supplement.pptx`를 별도로 준비해 드렸습니다).

- **"실전에서는 공격 위치를 미리 알아야 방어가 되는 거 아닌가요?"**
  → 지금 edge knockout은 매 요청마다 정확한 injection span을 알아야 지우는
  구조라, 말씀하신 지적이 맞습니다. head를 "찾는" 단계는 라벨이 있는 데이터로
  모델의 고정된 속성을 한 번 알아내는 것이라 문제없지만, knockout을 "적용"하는
  매 요청 단계에서 정확한 공격 문장 위치를 오라클처럼 안다고 가정한 건 단순화입니다.
  실전에서 말이 되려면 "외부 데이터 채널 전체"를 knockout 대상으로 삼아야 하는데,
  이 버전은 아직 검증하지 않았습니다.

- **"P2-d(InjecAgent 자체 head 탐색)는 7B에서도 되나요?"**
  → 아직 1.5B에서만 검증했습니다. `compute_head_relevance`를 반복 호출할 때
  GPU 메모리가 호출마다 누적되는 버그가 있어서, 60개 이상 InjecAgent case에
  대해 gradient 기반 head 탐색을 여러 번 도는 이번 실험은 1.5B로만 완료했습니다.

- **"jaccard(internal,external)이 왜 이렇게 높나요?"**
  → 아직 정확한 원인은 확인하지 못했고, 다음 단계(P3)로 계획하고 있습니다.
  `internal_heads − external_heads`와 그 반대(대칭차)를 보면 "자유 텍스트로
  낼지 tool-call로 낼지"를 가르는 채널 전용 head가 드러날 것으로 예상합니다.

- **"이 방법이 GPT-4 같은 API 모델에도 적용되나요?"**
  → 아니요. attention 확률과 gradient를 직접 뽑고 모델링 코드를 패치해야 해서,
  화이트박스로 접근 가능한 오픈웨이트 모델을 로컬(또는 자체 서버)에 올려야만
  가능합니다. API 뒤에 있는 폐쇄형 모델에는 적용할 방법이 없습니다.
