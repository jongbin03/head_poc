## 1페이지 — 타이틀

Read Head, Control Head 분리 PoC 확장 검증 발표하겠습니다. 모델 스케일업, Qwen2.5-32B와,
모델 패밀리 교차검증, Llama-3.1-8B, 두 가지를 다뤘습니다.

## 2페이지 — 서론

2차 발표에서 knockout이 7B 모델에서 공격을 억제하면서 정상 기능은 유지했지만, 절대적인
수치 자체는 낮았습니다. 이번에는 같은 실험이 더 큰 모델에서도, 다른 모델 계열에서도
재현되는지 확인했습니다.

첫 번째는 스케일 축입니다. Qwen2.5 7B에서 32B로, 같은 모델 계열에서 크기만 키워서 같은
실험을 반복했습니다.

두 번째는 패밀리 축입니다. Qwen2.5에서 Llama-3.1-8B로, 스케일은 7~8B로 고정하고 다른
아키텍처에서 같은 head 탐색과 knockout 파이프라인을 재실행했습니다.

## 3페이지 — 실험 환경

실험 환경입니다. 서버는 Titan RTX 24GB 세 장을 썼고, dtype은 bf16입니다. 스케일 축
모델은 Qwen2.5-32B-Instruct 4bit, 패밀리 축 모델은 Llama-3.1-8B-Instruct fp16입니다.
벤치마크는 AgentDojo — banking, slack, travel, workspace 네 개 suite를 사용했습니다.

## 4페이지 — Head 탐색 (Track A)

Head 탐색 방법입니다. AgentDojo를 두 트랙으로 나눴습니다. Track A는 탐색용으로, 단일
턴으로 잘라서 relevance를 계산합니다. Track B는 평가용으로, 멀티턴 agent loop에서
네이티브로 채점합니다.

탐색에서는 두 가지를 적용했습니다. 하나는 user_task 단위 group split — 같은 과업의
다른 injection이 탐색과 평가 양쪽에 섞이지 않게 통째로 한쪽에만 배정했습니다. 다른
하나는 suite별 층화 샘플링 — 특정 suite가 표본을 독점하지 않게 쿼터를 배정했습니다.

## 5페이지 — 평가 (Track B)

평가 방법입니다. AgentDojo의 실제 멀티턴 agent loop 안에 모델을 직접 끼워 넣고
실행했습니다. 토큰 확률 proxy가 아니라, tool을 실제로 실행한 뒤 환경 상태로 채점하는
네이티브 채점입니다.

조건은 두 가지입니다. k=0은 방어 없는 baseline, k=N은 찾은 head들의 D_inj 방향
attention edge만 차단한 knockout입니다.

지표도 두 가지입니다. utility는 원래 과업 성공 여부, security는 공격 성공 여부로,
낮을수록 좋습니다.

head 탐색에 쓰인 user_task는 평가 후보에서 제외했습니다 — held-out입니다.

## 6페이지 — 결과 개요

결과 개요입니다. 세 모델, 두 공격 전부 공격 성공률이 knockout 후 방향이 일관되게
낮아집니다 — 억제됩니다.

한 가지 눈에 띄는 점은, Qwen2.5-32B 모델에서 utility와 ASR이 둘 다 상승했다는
겁니다 — 스케일이 커져 성능이 향상될수록 공격 성공률도 같이 올라간다는 뜻입니다.

다만 Qwen2.5-7B 두 행은 구버전 파이프라인, held-out split 도입 전 결과라서
32B나 Llama-8B와 직접 비교할 때는 캐비엇이 필요합니다.

## 7페이지 — 스케일 축, Qwen2.5-32B / important_instructions

스케일 축, 32B에서 important_instructions 공격 결과입니다. utility는 knockout
후에도 유지되고 오히려 소폭 상승했습니다. 공격 성공률은 약 60% 감소했습니다. 공격
성공 사례는 slack에 집중돼 있고, 나머지 세 suite는 baseline부터 성공률이 낮습니다.

## 8페이지 — 스케일 축, Qwen2.5-32B / tool_knowledge

같은 32B 모델에 tool_knowledge 공격을 준 결과입니다. 공격 문구를 강화하자 baseline
공격 성공률이 8.77%에서 14.5%로 뛰었습니다. 그래도 knockout 후 억제 방향은
유지됐습니다. utility는 오히려 소폭 상승했습니다, 54.5%에서 56.4%로.

## 9페이지 — 패밀리 축, Llama-3.1-8B / important_instructions

패밀리 축, Llama-3.1-8B에서 important_instructions 공격 결과입니다. utility는
완전히 유지됐고, 공격 성공률은 4.5%에서 0%로 억제됐습니다. Qwen2가 아닌 다른
아키텍처에서도 같은 패턴이 재현된다는 뜻입니다. travel suite는 이번 파이프라인이
멀티 tool-call 응답 파싱을 지원하지 않아 제외했습니다 — 실제 성능 결과가 아닙니다.

## 10페이지 — 패밀리 축, Llama-3.1-8B / tool_knowledge

같은 Llama 모델에 tool_knowledge 공격을 준 결과입니다. 공격 성공률은 여기서도
4.5%에서 0%로 억제됐습니다 — important_instructions와 동일합니다. utility는
소폭 하락했습니다, 36.4%에서 34.1%로 — banking에서 1건이 knockout 후 실패로
전환됐습니다. travel suite는 위와 같은 이유로 제외했습니다.

## 11페이지 — 결론

정리하겠습니다.

스케일 축은 Qwen2.5 7B에서 32B로, utility는 유지하면서 공격을 60% 감소시켰습니다.

패밀리 축은 Qwen2.5에서 Llama-3.1로, utility를 유지하면서 공격을 억제했습니다.

두 축 모두 "공격 억제 + 정상 기능 보존" 패턴이 재현됐습니다 — 7B 단일 모델,
단일 공격 문구에서만 성립하던 효과가 아니었습니다.

다만 스케일이 큰 모델, Qwen2.5-32B에서는 baseline에서의 utility와 ASR이 기존
7B 모델 대비 둘 다 높게 나왔습니다.

## 12페이지 — 한계 및 다음 실험

마지막으로 한계 네 가지입니다.

첫째, 표본 크기입니다. suite마다 무작위로 15쌍만 평가했고 전수 평가는 아닙니다.
예를 들어 workspace는 실제 후보 pool 300에서 450쌍 중 15개만 썼습니다. suite별
전체 평가로 확대할 필요가 있습니다.

둘째, suite별 편차입니다. 공격 성공 사례가 거의 slack에만 몰려 있고, 나머지
세 suite는 baseline부터 0%인 경우가 많습니다. 결과가 slack 위주라는 것이고,
모델의 성능 문제인지는 추가 확인이 필요합니다.

셋째, AttnLRP, lxt 검증 아키텍처 범위입니다. head 탐색이 정상 동작을 확인한 건
지금까지 Qwen2.5와 Llama-3.1 두 계열뿐입니다. 같은 표준 구조를 쓰는 다른 모델,
Mistral이나 DeepSeek dense 계열 등으로 확장이 코드상 저비용으로 가능해 보입니다 —
다음 실험 후보로 제안합니다.

넷째, tool-call 파싱입니다. 100% 성공은 아니고 모델별로 70%대입니다. 실패한
턴은 tool 미실행으로 집계돼서 utility가 과소평가될 수 있습니다. 모델별 파서
정교화를 계속 진행하겠습니다.

이상입니다.
