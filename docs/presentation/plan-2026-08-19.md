## Part 2. 이후 실험 (6장)

### S4. [피드백 ②] 키 그룹 2 vs 모드 4
**부제**: "정상 vs 침입"이 아니라 "침입의 두 실행 경로"

| 구분 | 개수 | 목록 |
|---|---|---|
| relevance 계산 단위 | 3 | read, internal, external |
| 교집합(선정)에 쓰는 것 | **2** | internal, external |
| key span 종류 | 2 | `data_benign`, `data_inj` |
| 프롬프트 모드 | **4** | read_clean, read_injected, internal, external |

- 우측 ①: **internal/external은 둘 다 `data_inj`를 본다.** 차이는 backward 타깃뿐 — 자유 텍스트로 새는 경로 vs tool-call로 새는 경로
- 우측 ②: **`read_injected`는 head 탐색에 안 쓴다.** knockout **후** utility 검증 전용. `read_clean`은 숨은 명령이 없어 끊을 edge 자체가 없어서 이 검증에 못 씀
- 하단: 이 2×2 구조는 합성 데이터셋에서만 성립 — 실제 벤치마크는 tool-calling 단일 포맷이라 internal/external 구분이 구조상 없음 (→ S7에서 **채널 축을 소스 축으로 교체**)

### S5. [피드백 ③] 먼저 자체 진단 — 지금까지의 결론이 유효한가
**부제**: 새 실험보다 먼저, 기존 결론을 검사했다 (1.5B, 30템플릿)

| 진단 | 결과 | |
|---|---|---|
| 랜덤 head 기준선 | 선정 head: k=10에 0.91 → **0.0000** / 랜덤 동수: k=40까지도 **0.6448** | ✅ |
| jaccard 우연 기준선 | 0.538 vs 우연 기대 0.031 → **17.6배** | ✅ |
| top-K sweep | K=10에서 이미 완전 억제, K=20은 임계점 아님 | ✅ |
| dual-use head | `control_heads_both` 14개 중 **9개가 read top-20과 겹침** | ⚠️ |
| layer 0 지배 | 14개 중 **6개가 layer 0** (layer 0은 head 12개뿐 → 절반 차단) | ⚠️ |

- 하단: **"read/control이 완전히 분리"라는 1차 발표의 주장은 철회**한다 — "internal-external끼리의 겹침이 read와의 겹침보다 뚜렷이 크다"는 상대적 주장까지만 성립

### S6. [피드백 ①] AgentDojo를 어떻게 붙였나
**부제**: 탐색(Track A)과 평가(Track B)를 분리

```
                 ┌─ Track A (탐색)  단일 턴으로 잘라 relevance 계산 → 기존 인프라 재사용
  AgentDojo ─────┤
                 └─ Track B (평가)  실제 멀티턴 agent loop + 네이티브 채점 → 신규 구현
```

- 우측 ①: **왜 나눴나** — 탐색은 backward가 필요해 단일 턴이어야 하고, 평가는 반대로 실제 멀티턴이어야 의미가 있다
- 우측 ②: **네이티브 채점이란** — 토큰 확률이 아니라 tool을 실제 실행한 뒤 **환경 상태(잔액·전송된 메일)를 검사하는 결정론적 함수**. 교수님이 말씀하신 "제대로 된 성능 측정"에 대한 답
- 우측 ③: Track A 결과 949조합 → 필터 통과 **220쌍**. 걸린 문제: YAML 개행 정규화 / **인자 오염형 공격**(정상·공격이 같은 tool, 인자만 다름 → proxy로 구분 불가) / 토큰 충돌
- 하단: `KnockoutLocalLLM`으로 우리 HF 모델을 agentdojo 파이프라인에 직접 끼워, 롤아웃 내내 D_inj edge를 차단

### S7. 3소스 head 비교
**부제**: 채널 축(internal/external) → 소스 축(synthetic/InjecAgent/AgentDojo)

| 비교 | jaccard | 우연 대비 |
|---|---|---|
| synthetic ↔ InjecAgent | 0.308 | 12.2배 |
| synthetic ↔ AgentDojo | 0.214 | 8.5배 |
| InjecAgent ↔ AgentDojo | 0.290 | 9.5배 |

- 우측 ①: 집합 크기 synthetic 14 / InjecAgent 20 / AgentDojo 20, **합집합 36 · 교집합 5**
- 우측 ②: **3소스 교집합 5개가 전부 layer 0** — `(0,1) (0,3) (0,6) (0,7) (0,10)`. S5의 ⚠️가 소스를 3개로 늘려도 유지됨
- 그림: **3원 벤 다이어그램 신규 제작** (이 장의 핵심 시각자료)
- 하단: 세 소스가 무관한 head를 찾은 건 아니지만(우연 대비 8~12배) 같지도 않다 — 새 질문은 *"어느 소스의 head가 다른 소스에도 전이되는가"*

### S8. Track B 결과와 표본 문제
**부제**: 첫 멀티턴 신호, 그리고 늘리려던 두 손잡이가 둘 다 실패

**7B(4bit), 4 suite × 12쌍 = 48쌍**

| | utility | 공격 성공률 |
|---|---|---|
| k=0 (방어 없음) | 0.188 | **0.021 (1/48)** |
| k=14 (knockout) | 0.188 (변화 없음) | **0.000 (0/48)** |

- 우측 ①: **손잡이 A — 공격 문구가 약해서? → 아니다.** 가장 노골적인 `tool_knowledge`(정답 tool·인자를 문구에 박아넣음)로 교체해도 0.022 (1/46)로 그대로
- 우측 ②: **손잡이 B — 모델이 작아서? → 절반만 맞다.** 14B에서 utility는 0.188 → **0.267** (travel 0.00 → 0.11)로 오르지만 **공격 성공률은 0.022로 불변**
- 하단: 유일한 성공 공격이 knockout으로 실패로 바뀌고 utility는 안 깎였지만, **1/48이라 통계적으로는 아직 의미 없음** — 16GB GPU의 실용 한계(14B-4bit)까지 이미 써버린 상태

### S9. ★ 같은 모델·같은 head, 세 가지 측정
**부제**: 차이를 만드는 건 방어 효과가 아니라 측정 방법이다

14B + 동일한 13개 head

| 평가 방식 | 무엇을 재는가 | k=0 | knockout 후 |
|---|---|---|---|
| 합성 30개 (proxy) | 다음 토큰 확률 | **1.0000** | **0.0000** |
| InjecAgent 1,054개 (proxy) | 다음 토큰 확률 | **0.3347** | 0.0463 (7.2배↓) |

- 그림: **로그 스케일 막대 신규 제작** — 100% / 33% / 2%의 자릿수 차이가 눈에 보이게
- 우측: 합성 utility(read)는 0.9360 → 0.9515로 유지
- 하단: **proxy 지표가 실제 공격 성공률을 크게 부풀리고 있었다.** 교수님의 "성능 측정 방법도 제대로 된 걸로" 지적이 정확했다는 실험적 증거
